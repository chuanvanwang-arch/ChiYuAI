第 1 章　系统概述

1.1 软件背景

AI 原生智能销售管理平台（CRM-AI-Native）是一款面向企业 B2B 销售场景的智能客户关系管理软件。传统 CRM 以表单与流程录入为核心，销售决策高度依赖人工经验，且客户信息分散于邮件、表格与人员大脑中，形成信息孤岛。本软件以「AI 原生（AI-Native）」为设计理念，将智能体（Agent）、记忆系统、决策引擎与业务系统深度融合，使系统能够理解客户上下文、自动推进销售流程、辅助销售决策并执行审批闭环，把销售管理从事务记录升级为智能协作。

1.2 软件目标

本软件旨在实现以下目标：（1）以客户全生命周期为主线，统一管理线索、账户、商机、合同与回款；（2）通过多智能体编排与 MCP（Model Context Protocol）协议，将外部系统与智能能力接入销售流程；（3）内置 AI 决策引擎，对折扣、报价、审批等关键环节提供可溯源的建议与执行；（4）以多租户架构支撑 SaaS 化交付，并保证租户间数据与权限的严格隔离；（5）以配置驱动差异化，新增行业或业务域无需改动核心代码。

1.3 适用范围

本软件适用于制造、医疗器械、化工等行业的 B2B 销售团队、销售管理者及企业管理者，用于管理客户资产、推进销售机会、管控价格与折扣审批、沉淀销售知识并支撑经营分析。亦可作为智能体能力底座，经 MCP 协议被其他系统调用。

1.4 软件分类与特点

本软件属于人工智能软件，兼具企业级 SaaS（云计算）与信息安全属性。技术特点包括：AI 原生架构、多智能体协作、MCP 协议接入、向量化记忆与语义检索、多租户隔离、决策溯源与规则引擎、配置驱动行业差异化。

1.5 设计理念

「AI 原生」区别于「在旧系统外包 AI」：本软件将记忆、决策、智能体作为一等公民内建。写操作即构建知识（write-time indexing），每次交互自动沉淀记忆与本体；决策须可溯源至概念引用；对外能力以 MCP 工具形式暴露，使系统既是应用也是能力平台。

第 2 章　运行环境与依赖

2.1 开发与运行硬件环境

开发环境采用 x86_64 架构个人计算机（Intel Core i5 及以上 CPU、16GB 内存、512GB SSD）。运行环境为 x86_64 服务器或云主机（4 核及以上 CPU、8GB 及以上内存、100GB 及以上可用磁盘），支持容器化部署，可通过横向扩展提升并发能力。

2.2 操作系统与运行平台

开发操作系统为 Microsoft Windows 11；生产运行平台为 Node.js v22 运行时，支持 Windows Server 与 Linux（CentOS、Ubuntu）及 Docker 容器部署，具备跨平台能力。PostgreSQL 16 可独立部署于同机或专用数据库服务器。

2.3 运行支撑软件

核心支撑软件：PostgreSQL 16 数据库（启用 pgvector 向量检索扩展与 pgcrypto 加密扩展）；Node.js v22 运行时；Express 4 Web 框架；@modelcontextprotocol/sdk（MCP 协议实现）；pg（PostgreSQL 驱动）；dotenv（配置管理）；nodemailer（邮件通知）。

2.4 开发工具

软件开发环境包括：Node.js v22 与 npm 包管理器；Visual Studio Code 编辑器；Git 版本控制；Vitest 单元测试框架；TypeScript 类型检查；Playwright 端到端测试工具。

2.5 编程语言

后端与前端脚本采用 JavaScript（ECMAScript Module）；数据库采用 SQL 与 PL/pgSQL（存储过程与触发器）；前端页面采用 HTML5 与原生 JavaScript，通过 Express 静态托管。

2.6 网络与端口

HTTP 服务默认监听 3000 端口；MCP 服务经 StreamableHTTP 暴露（如 3001/mcp）；PostgreSQL 默认监听 5433 端口，schema 为 crm。生产环境建议前置 Nginx 反向代理并启用 HTTPS。

2.7 容量规划

单租户中等规模（万名客户、千条商机）下，PostgreSQL 配合 pgvector 索引可满足毫秒级语义检索；源程序约 6 万行，前端页面 78 个，整体资源占用低，适合中小集群部署。

第 3 章　总体技术架构

3.1 分层架构

本软件自顶向下包括：表现层（src/web 下 HTML 页面与前端脚本）、接入层（Express HTTP 服务与路由）、业务领域层（账户、商机、审批、合同、计费等模块）、智能层（决策引擎、智能体、记忆、知识、本体）、数据层（PostgreSQL 及向量扩展）、协议层（MCP 服务）。各层仅依赖下层，避免循环依赖。

3.2 核心目录

目录/模块职责
src/httpHTTP 服务入口与路由装配
src/account、src/sales客户账户与销售业务
src/approval、src/decision审批流与 AI 决策
src/agent、src/mcp智能体与 MCP 协议服务
src/memory、src/knowledge记忆与知识库
src/tenant、src/rbac多租户与权限
src/billing、src/contract计费套餐与合同
src/ontology、src/sevenDimensions本体与七维度决策
db/数据库 schema 与迁移脚本

3.3 数据流

前端页面经 Express 路由调用业务模块；业务模块通过 pg 驱动读写 PostgreSQL；决策与智能体模块在关键节点介入，调用记忆与知识库，并将结果回写数据库与事件总线（src/events），由监控与门户模块消费展示。所有写操作经决策第 0 闸校验。

3.4 事件总线

事件总线（src/events）覆盖任务、追踪、审批、粒子、支付等事件域，采用单连接 EventSource 推送，使前端看板与监控实时更新，避免轮询开销。

3.5 扩展性

通过 MCP 协议，外部智能体或业务系统可注册为工具提供方；通过配置中心，新增行业差异化策略无需改码。系统以插件化（connectors、skills）方式扩展能力。

第 4 章　安装、部署与备份

4.1 数据库初始化

node db/migrate.js # 建表与基础迁移 node db/migrate.js --seed # 载入种子配置

4.2 启动服务

npm run dev # 开发模式（热重载） npm start # 生产模式启动 HTTP 服务 npm run mcp # 启动 MCP 协议服务

4.3 测试与校验

npm test # 运行单元与集成测试 npm run audit:isolation # 多租户隔离审计

4.4 配置

系统通过 .env 文件配置数据库连接（PostgreSQL，默认监听 5433 端口，schema 为 crm）、密钥与邮件服务。配置项均为环境变量，不硬编码于源码。

4.5 Docker 部署

后端以 Node.js 镜像构建，PostgreSQL 以官方 16 镜像运行并挂载 pgvector；通过 docker-compose 编排，数据库数据卷持久化于宿主机。

4.6 反向代理

生产环境以 Nginx 前置，将 80/443 转发至 3000，并保留 /mcp 直连通道（客户端配置 http://IP/mcp 以避免 Authorization 丢失）。HTTPS 启用后裸 IP 访问返回 301 跳转。

4.7 备份与恢复

数据库经 pg_dump 每日逻辑备份；迁移脚本幂等，恢复时重跑 migrate 即可重建结构。配置中心与种子数据纳入版本管理，保证环境可重建。

第 5 章　用户、角色与多租户

5.1 用户与角色

系统内置 RBAC（基于角色的访问控制）。典型角色包括：租户管理员（admin，可通配本租户全部数据）、销售人员（sales，仅操作自有客户与商机）、审批人等。权限在路由层与数据层双重校验，避免越权。

5.2 多租户

系统以 tenant_id 作为租户隔离主键。每个业务表均携带 tenant_id，查询时由请求上下文解析当前租户，确保租户仅能访问本租户数据；平台管理员以通配符「*」进行跨租户运维。system 租户仅作为配置模板源，不直接承载业务数据。

5.3 登录与上下文

用户经 MCP 登录或 HTTP 登录获得身份，系统将其映射到租户与作用域（scope），后续所有写操作均经决策第 0 闸校验，未携带合法决策标识的破坏性操作将被拒绝。

5.4 角色清单

角色数据范围典型操作
admin本租户全部配置、审批、看板
sales自有客户/商机跟进、报价、提交审批
approver被指派审批实例通过/驳回/加签
platform跨租户（*）运维、诊断

5.5 权限矩阵

读操作按租户与作用域过滤；写操作除 RBAC 外还需经决策第 0 闸（executor）与决策场景硬闸（autonomyEngine）。仅引导式（bootstrap/autoDecision）或持 decision_id 的审批类操作可突破只读约束。

第 6 章　主要功能模块

6.1 客户与账户 360 视图

账户 360（account-360）页面汇聚客户基本信息、联系人、历史商机、合同、交互记录与 AI 洞察。系统基于记忆与知识库生成客户画像，辅助销售识别痛点与推进策略。客户提供统一视图，避免信息孤岛。主要数据项：账户名称、行业、规模、决策链、关键联系人、近期交互、健康度评分。

6.2 商机与销售流程管理

商机（Opportunity）沿销售阶段 S1–S6 推进，系统提供漏斗质量分析（funnel-quality）、阶段推进（stage-progression）与预测补差。销售可记录拜访、跟进与报价，系统对商机健康度进行评分。主要操作：新建商机、关联账户、更新阶段、记录拜访、提交报价。

6.3 审批流引擎

审批流（approval-flow）支持自定义阶段与签批人，覆盖价格、折扣、合同等关键节点。当销售报价超出权限阈值时，系统强制触发 CRM_APPROVAL_FLOW 审批，并将决策标识（decision_id）写入执行链路，确保治理闭环。审批支持加签、转交、撤回。界面元素含审批列表、详情、意见输入与决策按钮。

6.4 AI 决策引擎

决策引擎（decision）是软件智能核心，包含：（1）七维度（sevenDimensions）评估模型，从多视角对商机与报价打分；（2）决策图谱（decision-graph）可视化决策链路；（3）决策溯源（decision-provenance）记录每条建议的依据与引用；（4）规则引擎（ruleEngine）将业务规则数据库化，支持热更新；（5）决策先例（decision-precedent）复用历史经验。所有决策均可追溯至概念引用（concept_refs）。操作步骤：进入决策页 → 选择场景 → 查看七维度评分与溯源 → 采纳或驳回建议。

6.5 智能体平台与 MCP 接入

智能体平台（agent）提供 agent-workbench 工作台，支持智能体配置、事件触发器（agent-event-trigger）与编排。系统通过 MCP（src/mcp）对外暴露工具能力，使外部智能体或系统可经标准化协议读写销售数据、发起审批与查询洞察，实现「系统即能力」。配置项：智能体名称、绑定的技能（skill）、触发事件、授权范围。

6.6 知识库与记忆系统

知识库（knowledge）沉淀产品、竞品、方法论等文档，支持向量化检索。记忆系统（memory）维护跨会话的 append-only 日志与 curated 常驻笔记，结合 pgvector 实现语义检索，使智能体在后续对话中保持客户上下文一致性。写时自动向量化（write-time indexing），无需人工标注。

6.7 看板、合同与计费

看板（kanban）以任务卡片呈现销售活动与待办；合同（contract）模块管理合同起草、签署与回款（finance-receivables、invoice）。计费（billing）模块提供多档套餐，以席位（seatPolicy）、Token 配额（quotaGate）与功能权益（plan_entitlement）三道闸门控制租户能力，保证套餐权益单调递增。landing 页套餐区由 GET /api/billing/plans 动态驱动。

6.8 告警、监控与门户

告警规则（alerts）支持基于阈值的事件触发；监控（monitor）采集智能体健康度与业务指标；门户（portal，buddy-crm-portal）为统一工作台，聚合首页、看板、决策与配置入口，提供面向不同角色的视图。决策监控（sales-decision-monitor）提供 7×7 调整工具。

6.9 本体与语义

本体（ontology）模块维护领域词汇与语义关系，支撑写时向量化与语义检索，使系统自动构建可查询的知识图谱，降低人工录入成本。语义检索用于客户意图识别、相似商机匹配与知识推荐。

第 7 章　典型业务流程

7.1 价格审批场景

销售人员就某商机向客户报价，折扣超出自身权限阈值，须走系统审批。流程：（1）销售在商机页提交报价，系统检测折扣超阈值，自动调用报价引擎生成待审批单；（2）系统经审批流引擎启动 CRM_APPROVAL_FLOW，创建审批实例并通知审批人；（3）审批人查看 AI 决策建议（含七维度评分与溯源），执行通过/驳回/加签；（4）审批通过后生成 decision_id 写入执行链路，合同模块据此生成正式报价单；（5）全程事件经事件总线留存，监控与门户可追踪。该流程杜绝线下私下报价带来的治理缺口。

7.2 商机推进

销售新建商机并关联账户，按 S1–S6 推进；每阶段系统校验必填项与行为标准，缺失则提示。阶段跃迁触发漏斗质量评分更新，管理者于看板查看转化与预测。

7.3 合同签署与回款

审批通过的报价单可生成合同草稿，经签署流程归档；回款（finance-receivables）登记发票与到账，系统更新账户健康度与销售业绩。

7.4 异常处理

若审批被驳回，商机回到上一阶段，销售可依据建议修订后重新提交。所有写操作均经决策第 0 闸，缺 decision_id 且非引导式操作时拒绝执行，防止越权写入。

第 8 章　配置管理

8.1 配置中心

系统提供配置中心（config.html），以 config_store 为真相源，管理业务分层（business-tier）、审批流、告警规则、决策路由、先例等。所有阈值与行业差异均后台配置化，禁止在代码中硬编码域逻辑。

8.2 阈值与行业差异化

销售阈值（如折扣权限）通过 readThreshold() 从配置读取；不同行业的差异化策略以配置驱动，保证多租户架构纯净，不因新增行业而污染核心代码。

8.3 行为标准

行为标准（behavior-standard）配置定义销售动作规范，由方法层（method）在跟进、漏斗分类、阶段推进等环节校验执行，确保销售过程合规。

8.4 配置一致性

计费套餐以 config_store['billing-plans'] 为真相源，与种子 SQL、前端展示三源一致，并有常驻比对测试防止漂移；权益随档位单调递增，不得出现不限量档位被误配。

第 9 章　数据隔离与安全

9.1 租户隔离

所有业务表以复合主键（tenant_id, …）存储，写前经懒克隆（lazy clone）确保租户数据独立；跨租户查询由路由层透传租户上下文，测试套件内置隔离审计以防伪隔离。

9.2 权限与审计

RBAC 在路由与数据层双重生效；关键写操作经决策第 0 闸与审批流；系统记录确认审计（migration-confirm-audit）与决策溯源，满足合规可审计要求。

9.3 加密与凭证

密码经 pgcrypto 的 crypt() 哈希存储；敏感配置经环境变量注入，不落库明文；邮件等外部通知经 nodemailer 发送，SMTP 凭据不写入源码。

9.4 合规

系统提供审计包导出（governance-audit），含三闭环状态看板与合规数据，便于企业内审与外部审查。

第 10 章　维护与技术支持

10.1 日常维护

管理员通过管理控制台（admin）查看租户用量、决策健康度与参数诊断；通过 scheduler 执行定时任务；通过 report 模块导出经营报表。

10.2 版本与回滚

数据库迁移为幂等设计，支持增量迁移与回滚脚本；配置变更经配置中心管理，可对比基线，异常时可回退至历史版本。

10.3 故障排查

系统日志经运行日志文件记录；监控模块（monitor）与决策健康度（decision-health）提供实时诊断；隔离审计脚本可在测试环境校验多租户正确性。

10.4 技术支持

第 15 章　常见问题

Q1：报价无法提交？
检查折扣是否超权限阈值，超阈值须走审批流（CRM_APPROVAL_FLOW），系统将生成 decision_id。

Q2：跨租户看到数据？
运行隔离审计（npm run audit:isolation），确认复合主键与路由透传正确。

Q3：MCP 调用 401？
确认客户端配置 http://IP/mcp 直连，Authorization 头未被反向代理剥离。

Q4：数据库迁移报错 relation does not exist？
先执行 node db/migrate.js 建立基础表与配置，再 seed。

Q5：记忆检索不准？
确认 pgvector 扩展已启用，并执行 backfill 任务补齐向量索引。

第 16 章　典型界面与操作路径

16.1 首页（home）

首页聚合待办、看板入口、决策监控与快捷操作。销售登录后可见本周需跟进商机与审批任务；管理者可见团队漏斗与预测。顶部导航按角色呈现菜单（layoutMenu 由套餐权益控制）。

16.2 账户 360 界面

顶部为客户基本信息与决策链；中部为商机时间线与健康度；右侧为 AI 洞察（基于记忆与知识库）。操作路径：进入账户列表 → 选择账户 → 查看 360 → 点击「新建商机」或「记录拜访」。

16.3 决策界面

决策页（decision-thinking / decision-graph）左侧为场景选择，中部为七维度雷达与评分，右侧为溯源与先例引用。操作路径：选择决策场景 → 系统加载上下文 → 查看评分与依据 → 采纳或驳回并填写意见。

16.4 审批界面

审批页（approval-flow / approval-config）列出待我审批实例，详情含报价单、AI 建议与历史。操作路径：进入待办 → 打开实例 → 查看建议与溯源 → 通过/驳回/加签/转交。

16.5 门户界面

门户（buddy-crm-portal）为统一工作台，按角色聚合首页、看板、决策、配置与智能体。管理者可经业务看板（business-board）查看经营闭环。

第 17 章　集成与外部系统

17.1 MCP 工具注册

系统经 src/mcp 暴露工具，外部智能体通过 StreamableHTTP 连接 3001/mcp，以标准协议调用读写能力。工具需在配置中心登记作用域，避免越权。

17.2 连接器（connectors）

连接器模块（connectors）封装外部系统对接（如邮件、日历、工单），以确定性规则执行抽取与回写，LLM 仅在比价、分账等推理环节介入，保证主链路稳定。

17.3 技能（skills）

技能（skills）以可复用单元封装领域方法，智能体经 agent-workbench 绑定技能并编排，支持事件触发与自进化（沉淀、反思、修正）。

17.4 数据导出

系统支持经 report 模块导出经营报表（CSV/JSON），并经 MCP 或 API 供下游 BI 系统消费，形成数据闭环。

第 18 章　智能体编排与 MCP 调用示例

18.1 编排模型

智能体平台采用调度中心（kanban 任务调度）分派 worker 的执行模型：任务进入看板后由编排器派发至绑定技能的 worker，结果经事件总线回收。并发受限流与熔断保护，僵尸任务由治理线程回收，保证多智能体协作稳定。

18.2 MCP 调用示例

外部智能体经 StreamableHTTP 连接 MCP 端点后，以标准 JSON-RPC 形态调用工具。典型请求示意：

POST /mcp { "jsonrpc":"2.0", "id":1, "method":"tools/call", "params":{ "name":"crm_account_360", "arguments":{ "account_id":"ACME-001" } } }

系统校验 Authorization 与作用域后返回账户 360 视图；越权或缺失 decision_id 的写操作返回拒绝。该形态使任意兼容 MCP 的客户端复用本平台能力。

18.3 事件触发与沉淀

配置事件触发器（agent-event-trigger）后，满足条件的业务事件自动唤起智能体；执行结果经「积累—反思—修正」闭环沉淀为技能或配置更新，形成系统自进化。

第 19 章　测试与质量闸门

19.1 测试基线

系统以 Vitest 运行单元与集成测试，以 Playwright 运行端到端测试（e2e）。测试基线覆盖账户、商机、审批、决策、多租户隔离等核心链路，单次回归规模较大，隔离审计保证共享库下测试不互相污染。

19.2 质量闸门

提交前执行 UI 规范检查（ui-lint）强制约束前端页面结构与配色；多租户隔离审计（audit:isolation）阻断伪隔离；三源一致性比对防止配置漂移。任一闸门失败则阻断交付。

第 20 章　上线前检查清单

20.1 环境与依赖

确认 Node.js v22 运行时就绪；PostgreSQL 16 已启用 pgvector 与 pgcrypto 扩展；.env 中数据库连接、密钥、邮件配置完整且为环境变量注入，未硬编码于源码。

20.2 网络与端口

确认 HTTP 3000、MCP 3001/mcp、PostgreSQL 5433 可达；生产前置 Nginx 并启用 HTTPS，保留 /mcp 直连通道以避免 Authorization 头丢失；裸 IP 访问配置 301 跳转。

20.3 数据与隔离

执行数据库迁移与种子（node db/migrate.js --seed）；运行多租户隔离审计（npm run audit:isolation）确认复合主键与路由透传正确，杜绝伪隔离。

20.4 邮件与通知

核对 SMTP 凭据有效，发送失败应有回退日志；上线后抽样验证激活邮件可达，避免静默失败。

20.5 安全闸门

验证 RBAC 在路由与数据层生效、决策第 0 闸拦截无 decision_id 的写操作、密码经 pgcrypto 哈希存储。任一项异常须阻断发布。

第 22 章　数据备份与容灾

22.1 备份策略

数据库经 pg_dump 执行每日逻辑备份，输出 SQL 文本归档；迁移脚本（db/migrate.js）为幂等设计，可在新环境重建全部表结构与种子，保证环境可重建。生产环境建议对 PostgreSQL 启用 WAL 归档以实现时间点恢复。

22.2 恢复流程

恢复时先以迁移脚本重建结构（node db/migrate.js），再导入逻辑备份；配置中心与种子数据纳入版本管理，避免配置丢失。恢复后运行隔离审计确认租户数据完整。

22.3 配置与种子版本化

config_store、审批流、告警规则等以SQL种子与配置中心双源管理，变更可追溯；system 租户作为模板源不参与业务，租户首次访问时懒克隆，保证恢复后各租户独立。

第 23 章　性能与容量优化

23.1 向量检索优化

知识库与记忆的语义检索依赖 pgvector。对嵌入列建立 HNSW 或 IVFFlat 索引可显著提升相似度查询性能；新写入经 backfill 任务补齐向量，避免检索遗漏。嵌入维度在配置中心统一管理。

23.2 连接与并发

系统通过 pg 连接池复用数据库连接，控制并发上限；MCP 服务与 HTTP 服务共享同一数据层。多智能体编排受调度中心限流与熔断保护，避免数据库被瞬时高并发压垮。

23.3 前端与缓存

前端页面由 Express 静态托管，浏览器缓存静态资源；看板与监控经事件总线（EventSource 单连接）实时推送，避免轮询开销。配置中心缓存于内存，降低数据库读取频率。
