WHY AI-NATIVE

设备管理的真问题，不在"看见"，在"判断"

过去十年工业物联网解决了数据采集；接下来十年要解决的是：数据进来之后，谁来判断、依据什么判断、判断错了怎么纠正。

🌪️

告警风暴

几十上百台异构设备并发告警，阈值体系各自为政。运维真正缺的不是更多告警，而是"哪一条才是源头"。

🔗

连锁传导

A 设备异常引发 B、C 连锁告警。只看单机的系统必然误判源头，抢修方向错一次的代价远高于误报本身。

🧠

经验不可继承

老师傅的判别直觉留在人脑里，工单只记"已处理"。人员流动一次，组织记忆归零一次。

🧩

平台停在"看见"

主流工业互联网平台把连接、时序存储、组态看板、阈值告警做到了成熟，但"哪条告警是源头、该怎么处置、下次怎么更快"依然靠人。

我们的判断：连接与可视化已被工业互联网平台解决得很好，这块我们不重复造轮子，选择集成而非重建；真正没人解决的是判断与闭环——把经验变成可检索的记忆、把判断变成可解释的决策、把处置变成可复用的 SOP。ChiYu 正是补在这三件事上，并用分层智能体架构（边缘研判 + 集群归因）承接大规模设备群的算力与告警风暴。

业务亮点 01 · 设备全寿命周期一条轨道

从台账到复盘，不再人肉接力

台账 → 点检 → 监测 → 告警 → 诊断 → 工单 → 维修 → 备件 → 复盘，整条 EAM 链路内嵌平台，环节断裂自动预警。

  • 每台设备一份"活档案"：参数 / 备件 / 检修 / 改造全链留痕
  • 告警未转工单、工单超期未闭环、备件缺料自动预警
  • 状态只进不退，异常回退自动探测并留证
业务亮点 02 · 故障诊断方法论集成

判断不再靠"老师傅拍脑袋"

把成熟的可靠性与诊断方法固化成可调用的智能体能力，每一步都标注"用了什么方法、要什么输入"。

  • RCM 可靠性维修 / FMEA 失效模式 / FTA 故障树 / 5Why
  • 振动烈度（ISO 10816 类）、热成像、油液分析等判据接入
  • 原发故障 vs 次生告警判别，定位真源头而非噪音源
业务亮点 03 · 运维行为标准植入

好运维不是天赋，是可执行的标准

点检八定、交接班、持证作业、工单闭环、维修留痕，逐条可测评、可查、可复盘。

  • 点检前准备 → 点检中记录 → 点检后复核，闭环留痕
  • 工单响应与停留阈值有标尺，超阈值自动升级
  • "我的行为"达标看板，班组自驱改进

技术亮点 × 3

再让这套能力学会记忆、决策与复盘

不是数据库，而是会自检、会归因、会进化的设备中枢

技术亮点 01 · 设备记忆体 + 图谱 + 向量

从"设备台账"到"设备记忆"

设备—部件—测点—工艺—产线连成知识网，写库即构建；每一次运行、告警、处置都成为可语义检索的记忆。

  • 五类高频记忆自动沉淀：工况 / 故障与处置 / 部件与备件 / 工艺耦合 / 检修记录
  • "上次这台泵同样的振动频谱怎么处理的" → 秒级调出先例
  • 租户级 Know-How 隔离：你的故障库不会变成别人的训练集
技术亮点 02 · 认知决策引擎 · 每条结论可解释

告警不再黑箱，九尺子逐项打分

每条诊断结论 = 一条 9 列决策记录（场景 / 结论 / 置信度 / 依据 / 风险 / 概念引用…），写操作必经"决策第 0 闸"。

  • 九尺子 0–4 分制：8 项确定性判定可复现 + 1 项（清晰性）可选大模型精评，默认关闭
  • 缺什么信息就报什么，不放行、不静默通过
  • 处置建议必带依据与风险，并保留人工复核入口（工业安全红线）
技术亮点 03 · 复盘智能体 · 每一次处置都变成资产

经验每天被沉淀，教训自动变 SOP

复盘智能体定期扫描当期决策与工单，自动归因、产出可审查的复盘报告，结论回写设备记忆与故障知识库。

  • 批量归因 → 复盘报告 → 审批后沉淀（人工把关，不自动放行）
  • 误判复盘 → 修正判据阈值；成功处置 → 固化为标准处置卡
  • MTBF / MTTR 归因分析，指向"哪类设备、哪个部件、哪种工况"在吃利润
平台亮点 × 2

让这套能力扛得住大规模设备群，也复制得到别的设备类型

K-M-D 负责"判断可靠"，分层编排负责"算得过来"

平台亮点 01 · 认知驱动决策引擎 K-M-D

知识 → 方法 → 校验，三层管道

K 层装配设备记忆与工艺知识，M 层装载诊断方法论与行为标准，D 层用九尺子给每一次判断打分，结论携带概念引用，可一路追回依据。

  • 同一输入必得同一评分（确定性为主，大模型精评可选且默认关闭）
  • 处置链条与先例可检索、可比对，新员工 10 秒接手陌生设备
  • 结果回流校准：过于自信的判断被识别、下调置信度
平台亮点 02 · 分层自适应多智能体编排

设备级研判在边缘，集群级归因在云端

每台设备绑定边缘智能体做本地采集与异常研判，仅上报确认异常或跨设备疑点；集群协同智能体做聚合、根因与风险分级。

  • 单机异常边缘闭环不上送，缓解上下文溢出与算力开销
  • 断网可用：边缘独立研判，网络恢复后同步与补采
  • 设备类型、测点、判据、阈值全部配置化，换类型不改内核
ARCHITECTURE

三层智能体 + 一根认知支柱

下层解决"算得过来"，中层解决"判得准"，上层解决"落得下去"；右侧支柱保证每一次判断可解释、可追溯、可进化。

架构对照：工业互联网平台的告警多由中心化规则引擎产生——规则集中配置、阈值静态、越配越乱；这里改为分层自适应多智能体（边缘设备智能体 + 集群协同智能体），单机异常在边缘闭环，仅上报确认异常与跨设备疑点，从而抑制告警风暴、识别跨设备连锁；L2 业务层与右侧认知支柱是 ChiYu 相对工业互联网平台的增量——把根因结论真正变成工单、备件、排程动作，并把处置经验沉淀回记忆与知识库。
BENCHMARK

对标现有工业互联网平台：差异不在"连得多"，在"判得准、落得下"

主流平台的核心范式是"连接 + 时序存储 + 组态看板 + 阈值 / 规则告警"，这块已经很成熟。真正的差异发生在告警之后：谁来判断源头、依据什么判断、判断之后谁把它闭环。

DELIVERY PATH

建议的落地节奏

先小范围验证链路闭合，再扩设备、扩厂区。

STEP 01

单设备类型 PoC

选一类设备（如泵站 / 空压机 / 暖通机组）接入历史数据与故障记录，验证记忆构建、根因判别与复盘回写是否闭合。

STEP 02

集群级试点

扩至一个厂区的设备集群，验证告警收敛率、原发/次生判别准确率、工单闭环率，指标实测后回填本材料。

STEP 03

多类型复制

以配置画像方式复制到其他设备类型，不改内核代码；租户级知识隔离，跨厂区经验可选择共享或隔离。

前置条件（需客户侧确认）：① 历史运行与故障数据的可得性与质量；② 工艺耦合关系（设备—产线拓扑）是否可梳理；③ 边缘算力与网络条件；④ 与既有 MES / CMMS / OPC-UA 的对接方式；⑤ 人工复核与放行权限的归属。以上未明确前，不承诺上线时间与量化收益。
