# method-role-map · 维度释义（references/dimensions.md）

## D · 决策者 Decision Maker

- 最终拍板人是谁（CEO/VP/采购负责人）？预算审批链几级？
- 我们接触的是决策者本人还是秘书/助理？`payload.business_title` 是否为 C 级/VP 级？
- 反例：一直跟使用部门聊、从未触达拍板人 → D 未满足，是最大风险。

## I · 影响者 Influencer

- 谁的意见影响决策：技术评审（CTO/架构师）、财务（ROI 核算）、法务（合规）？
- 影响者立场关键——技术影响者否决=方案被技术上架；财务影响者否决=预算被砍。
- 证据：`payload.influencers` 名单 + 是否已与其直接沟通。

## U · 使用者 User

- 谁每天用系统（销售一线/客服/运营）？他们的痛点由谁代言？
- 使用者热情是推进燃料：`payload.champion` 若来自使用者层，识别其是否够格影响决策。
- 反例：用户喜欢但决策者无感 → 仍需打通 D，用户热度不能替代决策链。

## S · 利益相关方 Stakeholder

- 谁会被方案波及：合规/运维/采购/信息安全？
- 关切点常是后期的否决点：数据合规、权限审计、系统集成——`payload.stakeholders` 逐一列出。

## 与其它方法论衔接

- D/I/U/S 与 MEDDICC 的 E1（经济买家）/C1（冠军）互补：MEDDICC 回答「有没有」，角色地图回答「是谁、什么立场、怎么打」。
