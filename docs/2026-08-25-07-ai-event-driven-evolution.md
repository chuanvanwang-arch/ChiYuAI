## 0. 核心立场：预警 = 事件驱动统一源，而非定时任务

> **事件驱动进化 = 把"智能体越用越强"做成事件驱动、有判据、有回测的工程回路。在 CRM 域，预警不是"规则引擎 + 定时任务周期扫描"，而是统一事件源（粒子写事件 / 外部连接器事件 / 审批节点事件）→ 事件总线 → 预警 / 回收 / 补偿 / 记忆 / 反馈全链路挂载。**

CRM 关键判别（对照 Q.19 差异点）：

- **D4 预警事件化**：官方 CordysCRM 预警 = 规则引擎 `operator+condition` 配置 + 定时任务周期巡检（人配条件、机器扫）。我们 = **预警源统一定义为事件**，与业务写操作同源（粒子写钩子即发射点），AI 可参与判断（严重度分级 / 处置建议），事件进审计与反馈闭环，而非"配好规则等人看"。
- **D11 连接器化**：外部数据源（标讯 / 工商）= 双向连接器 + 统一事件总线，既对外接技术能源、又对内灌数据源，不是内嵌功能模块。
- **D12 原生化总差异**：上述差异是"能力从第一行代码长出来（事件/状态机/反馈回路原生内建）"vs"在旧底座上外层叠加技能封装"在"事件"维度的集中体现。

## 1. 方法论依据（跨域通用核心）

> 本能力是**事件触发式能力进化方法论**。以下提炼其通用法则 / 铁律 / 判据 / 模式，保持跨域通用，不绑定任何具体项目专有名词。CRM 实例化见 §3。

**核心心智模型**：

> 进化 = 事件 → 评估判据 → 沉淀 / 修正 → 效果回接。四个环节缺一不可：没有判据是乱改，没有回接是盲改。

**三型进化动作（触发条件不同）**：

| 动作 | 触发事件 | 判据 | 操作 |
|---|---|---|---|
| **沉淀 Accumulation** | 完成多步任务 / 修好疑难错误 / 发现可复用工作流 | 别人重做要重新踩坑的 | 新建技能，记全步骤与坑 |
| **修正 Correction** | 使用 / 阅读技能时发现缺陷 | 错字、过时命令、缺步骤、误导描述 | 立即修，不问用户 |
| **反思 Reflection** | 技能被使用之后 | 有更好工作流 / 边界 / 前置条件值得记录 | 有意义才更新，无意义不 churn |

**沉淀五判据（须同时满足）**：① 可复用（他人 / 未来的自己不必从零摸索）；② 有代价（典型信号：8+ 工具调用 / tricky error / 非平凡工作流）；③ 非一次性；④ 无敏感信息；⑤ 未被覆盖。**跳过沉淀是允许的，但须是有理由的决策**。

**评估闸门作为触发源（对接反馈闭环）**：质量闸门的评估事件是进化回路最重要的新信号源——① 同类 redo 连续 ≥N 次 → 大概率是评估标准或技能缺陷 → Correction；② human_override（人改判）→ 评估标准系统性偏差 → Correction 校准阈值；③ 首次交付合格率持续下降 → 技能质量退化 → Reflection。**铁律：评估事件只是候选信号，仍须过置信度判据（连续次数阈值）才触发，防噪声 churn。**

**从属性轴驱动进化事件（通用范式）**：J_Judge 评分与人工结论持续偏离（连续 N 次置信度 <0.7）→ Correction；F_Forecast 预测与实际偏差超阈值 → Accumulation；C_Compliance 发现新模式 → Accumulation 沉淀规则；A_Alert 告警频率超基线 → Correction/Accumulation；C_Classify 发现未知分类值 → Accumulation。经验：M_Multimodal / O_Optimize 通常不触发进化；`confidence < 0.6` 的派生属性值不应触发进化。

**防 churn 铁律**：反思后若无实质改进，**不修改技能**——为"看起来在进化"而改是技能库最大风险。工程化：反思四问任一有实质内容才 `improved:true` 并合成经验；全空 → `improved:false` 不写。

**置信度校准（什么该进技能）**：高置信（进技能）= 已验证步骤流程（跑通过）/ 踩坑根因与确切修法 / 明确工作流判据阈值；低置信（进记忆 / 不沉淀）= 猜测假设未验证方法 / 单次环境偶发 / 客户特定一次性方案。

**效果回接闭环**：`沉淀 / 修正 → 回测（重跑核心路径）→ 通过 → 记录版本；失败 → 修正技能 → 重测`。**回测不是可选项**：修改后不验证 = 把未验证假设写进知识库。

**防漂移清单（6 条）**：① 不 churn（无实质改进不修改）② 不回测不发布 ③ 不膨胀（沉淀有判据）④ 不越权（删除 / 重构先问用户）⑤ 不静默覆盖（冲突显式声明）⑥ 不记敏感。

**HITL 治理**：沉淀 = 模型自主（低风险）；**删除 / 批量重构技能必须经用户同意**；技能库混乱（重复 / 命名冲突 / 职责重叠）→ 提醒用户整理，不擅自批量重构；新技能与现有技能职责重叠 → 描述中互相引用并说明边界，不静默覆盖。

**双轨进化**：事件轨（运行时事件自动 + 即时）vs **夜间轨**（跨对话综合 memory_log + 会话日志 → 聚类找模式 → 生成技能草稿 / 反写提案 → **HITL 审批后才生效**）。夜间轨解决事件轨"只见单点、看不到跨对话模式"的盲区；草稿绝不自动生效。

**实践心得（通用工程铁律，落地必守）**：
1. 事件与任务必须分表：事件 = 信号 / 幂等消费（`idempotency_key` 唯一 + `status: pending/consumed/ignored`）；任务 = 工作 / 有状态，两概念不可混淆。
2. 防 churn 是护栏不是建议：用类型 / 判据直接 `ignored`，并有负向用例守护。
3. 回测必须返回"刷新后的对象"：INSERT（draft）→ 回测改库为 validated 后**务必重新 SELECT**，否则调用方拿到陈旧 draft。
4. 沉淀判据须结构化返回：`{shouldAccumulate, reasons, reason}`，让"已覆盖""churn"分别给出可观测拒因。
5. 集成触发要 guarded：业务动作末端"偏差超阈值 → 发射事件"用 try/catch 包裹，发射失败不阻断主流程（fail-open）。
6. **发射点存在 ≠ 事件落表——运行时验证才算闭环**：新事件类型注册后须确认既有代码有发射点，且事件表对应类型确有数据；否则是"纸面事件"，白占判据。

## 3. 落地设计（CRM 销售域实例化）

### 3.1 事件总线（5 事件域，复用已验证 SSE 总线底座）

沿用总体架构 §1 接线不变量与已验证 SSE 总线契约，事件分为 5 域：

| 事件域 | CRM 承载 | 预警相关 |
|---|---|---|
| `particle` | 业务粒子写事件（DEAL/ACCOUNT/CONTRACT 状态变更、价格变更） | 超期未跟进 / 商机卡顿 / 合同到期 / 价格联动 的底层源 |
| `payment` | 回款计划 / 记录事件 | 回款逾期 |
| `approval` | 审批节点事件 + 回滚补偿事件 | 审批节点事件 / 审批回滚 |
| `trace` | 外部连接器事件（标讯 / 工商变更） | 标讯推送 / 工商校验 |
| `task` | 预警派发的处理任务（回收 / 催收 / 续约待办） | 预警动作落地 |

**接线不变量**：一切业务写操作（人 / 智能体 / 外部连接器）→ 统一进粒子写通道 → 触发粒子写事件 → 事件总线广播；本体 / 向量构建、记忆捕获、预警扫描、审计、反馈全部挂写事件，互不阻塞主事务；读操作不写事件。

### 3.2 预警事件源全集的事件定义与触发条件

| 预警事件（type） | 域 | 触发条件（事件源） | 挂载动作 |
|---|---|---|---|
| `LEAD_FOLLOW_OVERDUE` | particle | `deal.stage=lead` 且 `lastActivityAt` 超过 `org.pool_config.recycle_rule.threshold` | `crm-lead-recycle`（过闸写 Action）+ 入审计 / 反馈 |
| `OPP_STAGE_STUCK` | particle | `age_in_stage` 超阶段阈值，或 `win_probability_adjusted` 低且停留久 | `deal-coach` 推进建议 + 门户待办 |
| `PAYMENT_OVERDUE` | payment | `plan.due_date < now` 且 `record` 未核销 | 催收提醒 + 财务待办 |
| `CONTRACT_EXPIRY` | particle | `contract.end_date - now < N` 天 | 商务预警 + 续约待办 |
| `TENDER_PUSHED` | trace | 标讯连接器订阅匹配命中 | `lead-miner` 提炼线索 + 门户推送 |
| `APPROVAL_NODE_EVENT` | approval | 审批节点状态变更（提交 / 通过 / 驳回 / 加签 / 抄送） | 待办派发 + 回滚补偿钩子 |
| `PRICE_CHANGED` | particle | `price-list` 变更 / 过期 → 关联报价自动同步 | 价格变更日志 + 审计事件 |

### 3.3 外部事件源：双向连接器 + 统一事件总线（D11）

```
标讯连接器（大单网）          工商连接器（企查查/爱企查）
  入站：订阅推送命中              入站：工商变更 / 校验结果
    → TENDER_PUSHED(trace)          → ACCOUNT 写时校验事件(particle)
  出站：主动查询探测（建议）        出站：校验请求
        │                              │
        └──────── 统一事件总线 ────────┘
                    │ 先入 trace/particle 事件表
                    ▼
      下游驱动：粒子写（建 lead）/ 预警 / 记忆 / 审计
```
- **fail-open**：连接器发射失败 / 外部源不可用 → try/catch 包裹，不阻断主业务写入。
- **写时校验闸**：标讯字段 schema 校验、工商统一信用代码校验，失败落标记（auto_weak 边待人工确认），不静默吞。

### 3.4 审批回滚补偿机制

- `APPROVAL_NODE_EVENT`（通过 / 驳回）→ 结果后动作（`result_action`）触发数据变更 → 变更**挂补偿（compensation）钩子**。
- 补偿 = 写管线内建机制：upsert 幂等 + 补偿双保障。驳回 / 失败后动作失败 → 触发回滚到审批前状态。
- 事件体现：`APPROVAL_COMPENSATION` 事件入 `approval` 域，记录回滚前后快照，进审计轨迹。

### 3.5 事件触发 SKILL 沉淀 / 进化机制（对接 §1 方法论）

| 进化动作 | CRM 触发事件 | 判据（防 churn） |
|---|---|---|
| Accumulation | 某客户反复 `PAYMENT_OVERDUE` 连续 N 次 / 标讯→线索筛选成可复用工作流 | 别人重做要踩坑 + 五判据满足；低置信只落记忆 |
| Correction | 预警误报（人 dismiss / override）连续 N 次 | 阈值系统性偏差 → 校准 `APPROVAL_NODE_EVENT`/预警阈值 |
| Reflection | 预警处置动作被使用后 | 反思四问有实质内容才 `improved:true`，否则不 churn |

- **置信度闸门**：`confidence < 0.6` 的预警 AI 判断**不触发沉淀**；评估事件须过连续次数阈值才触发，防噪声 churn。
- **双轨进化**：运行时事件轨即时生成预警处置经验草稿；夜间轨跨对话综合 → 进化草稿进治理视图审批队列（HITL），**草稿绝不自动生效**。
- **回测闭环**：预警阈值 / 处置规则修正后重跑核心路径（如"改阈值后该预警是否仍误报"），通过才 validated。

### 3.6 AI 参与判断（D4 核心差异）

预警不是纯阈值触发——AI 参与：

- **严重度分级**：`A_Alert` 频率超基线 / `J_Judge` 参与 `severity: info|warn|critical`，非单纯条件命中。
- **卡顿判定**：`OPP_STAGE_STUCK` 结合 `win_probability_adjusted`（赢率校准）+ `age_in_stage`，而非仅停留天数。
- **回款风险**：`customer_health_score` 参与 `PAYMENT_OVERDUE` 风险分级与催收排序。
- **处置建议**：预警事件挂载 AI 生成的下一步动作建议（进门户待办），人确认后执行。

### 3.7 事件 Schema / 接口草图

```ts
// 统一事件信封（5 域）
interface DomainEvent {
  id: string;                          // 幂等键 idempotency_key
  domain: 'task'|'trace'|'approval'|'particle'|'payment';
  type: string;                       // 如 LEAD_FOLLOW_OVERDUE / TENDER_PUSHED
  ts: number;
  source: string;                     // 粒子写钩子 / 外部连接器 / 审批引擎
  payload: Record<string, unknown>;
  confidence?: number;                // AI 参与判断的置信度（<0.6 不触发沉淀）
  status: 'pending'|'consumed'|'ignored';  // 幂等消费三态
}

// 预警专用派生
interface AlertEvent extends DomainEvent {
  domain: 'particle'|'payment'|'approval'|'trace';
  severity: 'info'|'warn'|'critical'; // AI 参与严重度分级（J_Judge）
  action_ref?: string;                // 挂载的写 Action / 待办任务
}

// 消费契约：幂等 WHERE status='pending' 条件更新，二次消费返回 false
// 发射点须真实存在且事件表有数据（防"纸面事件"）
```

## 4. 与其他能力 / 四平面的接口

**核心挂点**：L2 事件平面（总体架构 §1 四平面）。本能力是横切接线层，不持有业务状态，只消费与广播事件。

| 对接能力 | 接口形态 |
|---|---|
| **ai-particle-system-design**（L1） | 被粒子写钩子触发：粒子写事件 → 事件总线（L1→L2 接线不变量①）；事件驱动回收 / 价格联动落粒子写通道 |
| **ai-ontology-vector-build**（L1） | 预警 / 审批 / 外部事件触发的记忆与本体边更新走写时向量化（embedding 覆盖率监控覆盖评估域） |
| **ai-memory-lifecycle**（L2+L3） | 预警事件 / 审批事件 → 记忆流（快照 / 推理）；进化结论沉淀回记忆（技能=可执行步骤，记忆=信息性事实） |
| **ai-feedback-loop**（L2） | 预警触发指标埋点（新线索+1 / 回款逾期率）；对账结果（计划 vs 记录）自动触发动作，预测偏差回灌 |
| **ai-capability-audit**（L2） | 所有预警 / 审批 / 外部调用事件全量入审计轨迹（谁 / 何时 / 触发了什么）；价格变更日志 = 审计输入 |
| **ai-multi-agent-orchestration**（L3） | `APPROVAL_NODE_EVENT` → kanban 派发审批任务；`blocked(approval)` 等待 HITL，不归 failed；预警处置任务派发 |
| **ai-native-action-design**（L3） | 预警挂载的回收 / 催收 / 续约 = `crm-*` 写 Action，统一过闸（规则层 + action-confirm + HITL） |
| **ai-portal-page-generation**（L4） | 预警 / 审批待办 → 四视角待办工作台；进化草稿进治理视图审批队列（HITL） |

## 5. 验收判据（来自 §5ter 覆盖 + D4/D11 差异点，可验证）

1. **预警事件化全集落库**：7 类预警事件（`LEAD_FOLLOW_OVERDUE` / `OPP_STAGE_STUCK` / `PAYMENT_OVERDUE` / `CONTRACT_EXPIRY` / `TENDER_PUSHED` / `APPROVAL_NODE_EVENT` / `PRICE_CHANGED`）均有发射点且事件表对应类型**有数据**（呼应"发射 ≠ 落表"实证）。
2. **预警触发 = 事件驱动为主 + 规则治理兜底**（2026-08-26 修订口径，对齐实现）：
   - **事件驱动为主**（D4 核心）：预警首选由写事件 / 外部连接器事件触发（粒子写钩子即发射点），AI 参与判断（severity/confidence），事件进审计与反馈闭环。
   - **规则治理兜底**：组织配置驱动的周期扫描（如 `src/scheduler/timers.js` 30min `runRiskScan` / lead 池回收扫描）只做「规则治理检查 → 发射预警事件」——**扫描不直接跨粒子写**，回收 / 处置动作仍由 `crm-*` 写 Action 经写通道第 0 闸显式触发。此兜底是「规则驱动数据产生」（治理纪律），非「预警业务逻辑定时执行」，与 D4「预警=事件驱动统一源」不冲突。
   - **判据**：任何定时扫描若直接写粒子（绕过 Action 三闸）即违规，归入「定时任务式预警」反模式。
3. **外部事件源双向连接器**：标讯 / 工商连接器接好，事件先入 `trace`/`particle` 域事件表再驱动下游；外部源不可用时不阻断主流程（fail-open）。
4. **审批回滚补偿**：`APPROVAL_COMPENSATION` 事件落表，驳回 / 失败后动作失败可回滚到审批前状态（§5ter.11 实证）。
5. **AI 参与判断**：预警事件含 `severity` / `confidence` 字段（J_Judge 参与分级），非纯阈值条件。
6. **事件与任务分表 + 幂等消费**：事件表 `idempotency_key` 唯一 + 三态消费；同一事件重复触发只建一个任务。
7. **防 churn**：预警阈值校准走置信度判据（连续 N 次 override 才 Correction），无实质改进不新建 / 改 SKILL。
8. **D4 验收**：预警 = 事件驱动统一源（非规则引擎 + 定时任务）。
9. **D11 验收**：外部数据源 = 双向连接器 + 统一事件总线（非内嵌功能）。
10. **§5ter 覆盖**：线索池回收 / 商机卡顿 / 回款对账 / 合同到期 / 标讯 / 审批 / 价格联动 全部有事件源且进审计 / 反馈闭环。

## 6. 不做的事（YAGNI + 不借鉴 CordysCRM 规则引擎 / 定时任务式预警）

- **不建独立规则引擎配置表 + 定时任务周期扫描做「预警业务逻辑」**（官方 CordysCRM 预警模式，D4 明确不借鉴）→ 预警统一走事件总线，由写事件 / 外部事件触发。
- **允许「规则治理兜底扫描」但限定边界**（2026-08-26 补充）：组织配置驱动的周期扫描（timers.js 30min riskScan / lead 池回收）只「规则检查 → 发射预警事件」，**禁止直接跨粒子写**；回收 / 处置必须经 `crm-*` 写 Action（写通道第 0 闸）显式触发。任何「定时扫描直接写粒子 / 绕过 Action 三闸」即违 D4，归入反模式。
- **不做"预警 = 单纯条件配置给人看"** → 我们预警事件进审计 / 反馈闭环，且 AI 参与判断（严重度 / 处置建议）。
- **不做审批独立系统**（配置表 + 代码逻辑，官方形态）→ 审批 = HITL 闸 = 编排决策节点（D5，属 orchestration 能力边界）。
- **不做连接器内嵌功能**（官方内嵌标讯 / 工商）→ 连接器组件 + 统一事件总线（D11）。
- **不建"纸面事件"**：只定义 + 消费两端但全库无发射点、事件表无数据者不落地（§1 实践铁律 6）。
- **不沉淀 `confidence < 0.6` 的预警判断、不 churn**：无实质改进不新建 / 改 SKILL（防漂移清单）。
- **不自动生效进化草稿**：夜间轨生成的 SKILL 草稿须经 HITL 审批（治理铁律）。
- **不侵入智能体推理 / 记忆存储实现细节**：属 orchestration / memory 能力，本能力只负责事件的消费、广播与进化触发。
