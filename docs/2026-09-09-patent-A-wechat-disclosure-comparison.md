## 三、逐点详析（附原文引证）

### 3.1 九尺子混合评分（#1）—— 🟢 完全未披露（最强创新点）

公开文中与"评分/维度"相关的最接近表述：
- s30:36「线索评分（**20 维度打分排序**）」—— 这是**线索评分（lead scoring）**组件，非决策裁决评分，且维度数与机制均不同。
- s27:39「加权判据（准确性 40% / 合规性 25% / 完整性 20% / 可用性 15%）」—— 这是 **Evaluator 质量闸门**权重，非决策引擎的九尺子。

二者皆非 A 件的"8 确定性规则 + 1 LLM 输出混合裁决"结构。**该点可作为 A 件最具区分度的独立权利要求。**

### 3.2 红线优先强制 HITL（#2）—— 🟡 概念披露，结构安全

公开文命中：
- s09:33「人机协同闸门<small>**红线决策留给人**</small>」
- s09:151「① 入口·人机协同闸门｜**红线决策怎么留给人**、建立信任边界？」
- s22:28「HITL 指关键节点必须由人确认，AI 才能继续」

这些是**架构/管理原则层**的表述，描述的是"红线类决策应保留给人"。但 A 件的核心是**代码层的判定顺序**：`autonomyEngine.js:244` 在置信度反算之前先做红线/EXCEPTION 硬判定，触线即强制 HITL，**无论置信分多高**。公开文从未披露"判定顺序"与"置信分被红线覆盖"这一技术机制。

> ⚠️ **撰写警示**：独立权利要求**不能**写成"一种将红线决策留给人的方法"（已是公开概念），必须写成"……**在基于置信度确定自主执行或人工确认之前，先执行红线规则硬判定，若命中则强制转入人工在环、屏蔽置信度自主放行分支**"。

### 3.3 决策落库 schema（#3）—— 🟢 完全未披露

公开文对"决策记录"的描述（s11:63-65）是方法论："记全（记原因/谁拍板/参考先例）、连起来（决策间引用）、治理"。**无任何字段级 schema 披露**，更无 `concept_refs`（关联概念引用）、`effective_policy_version`（裁决时冻结的政策版本）等 A 件特有字段。该落库结构可作为从属权利要求重点保护。

### 3.4 置信度反算（#4）/ 权重外置（#5）/ 证据双路合并（#6）—— 🟢 均未披露

- 置信度：公开文仅 s04:69、s06:46「**判断置信度**」（业务动作描述），无算法、无 `0.7/0.8` 参数、无"反算"一词。
- 权重：s27 的权重属 Evaluator，与决策 rubric 权重外置无关。
- 证据双路：s10「AI 说话有据可查」为原则，无"双路知识源合并"实现。

### 3.5 决策可审计追溯（#7）—— 🟡 概念披露，结构安全

s11:43「参考了哪些过往**先例**」、s11:63「这次判断引用了哪次先例」描述决策引用先例的理念；s13:50「合规红线…**有据可查的建议**」。这些是"决策应可追溯"的理念，未披露 decision_id 串接先例+政策版本冻结的**具体数据模型与查询路径**。结构层安全。

## 五、权利要求策略修正（基于比对结果）

### 5.1 独立权利要求锚定结构（推荐写法骨架）

```
1. 一种基于多智能体编排的销售决策辅助方法，其特征在于，包括：
   S1 接收销售决策请求，解析决策场景与上下文；
   S2 调用评分模块，对所述请求并行执行 N 条确定性评分规则
      与 1 条大模型输出，获得各自评分与依据（所述 N≥5）；
   S3 按外置权重配置对 S2 的评分结果加权聚合，反算综合置信度；
   S4 在依据所述综合置信度确定自主执行或人工确认之前，
       先执行红线规则硬判定；若命中红线，则强制转入人工在环，
       屏蔽基于置信度的自主放行分支；
   S5 将决策结果及所述依据、所引用先例、裁决时生效的政策版本
       写入决策记录并分配决策标识，形成可审计追溯链。
```
