## 1. 背景与目标

目标是构建一个**基于 AI 原生的销售管理平台**。已按 AI-* 方法论完成 10 个能力设计：

ai-particle-system-design / ai-ontology-vector-build / ai-context-layering /
ai-memory-lifecycle / ai-native-action-design / ai-multi-agent-orchestration /
ai-event-driven-evolution / ai-portal-page-generation / ai-feedback-loop / ai-capability-audit

候选方案两个：
- 方案 1：基于 CordysCRM 进行修改。
- 方案 2：与 PDM 类似，从无到有开发。

本文档给出选型判断（§2）、三阶段执行路径（§3）、CordysCRM 值得借鉴清单（§4）与明确不借鉴清单（§5）。

## 2. 选型结论：方案 2（从无到有，PDM 同构）

### 2.1 核心判据：你要的是「AI 原生平台」，方案 1 是「功能加固」

10 个 AI-* 设计是**平台级蓝图**，描述的是一个从第一行代码就按粒子系统生长的平台。方案 2 是这 10 张蓝图的**直接实例化**：

| 能力 | 方案 2（从无到有） | 方案 1（改 CordysCRM） |
|---|---|---|
| 粒子级数据模型（ai-particle-system-design） | 从建表起就是粒子 | 逆向套在 JPA/Hibernate + `field_value` 动态字段表之上 |
| 本体+向量写时构建（ai-ontology-vector-build） | 建表即建向量索引 | 需在非粒子模型上叠加，语义不对齐 |
| 记忆三构件 | 原生落在 PostgreSQL+pgvector | 需外部挂接 |
| 多智能体编排（ai-multi-agent-orchestration） | agentLoop/kanban 直接接线 | 需把别人家的业务代码改造成可派发 |
| 事件驱动进化/反馈闭环/审计 | 原生机制 | 逆向套在别人家功能上 |

方案 1 的**结构性冲突**：CordysCRM 的模块化字段模型（`field_value` 表 + 137 个 MySQL 方言 Flyway SQL + JPA 动态查询）是**给「人配置表单」用的**，与「AI 主动写对象/构建本体」的粒子模型**语义不对齐**。这不是改多少行代码能解决的，是模型形态冲突。

### 2.2 详细对比（基于证据）

| 维度 | 方案 1：改 CordysCRM | 方案 2：从无到有（PDM 同构） |
|---|---|---|
| 数据模型 | 模块+字段可配置表，非粒子级 | 直接按粒子设计建表，零历史包袱 |
| 10 大能力落地 | 逆向套在 JPA/Hibernate + 137 个 MySQL 方言 SQL + 73 个 Mapper XML 之上 | 蓝图原生实现 |
| 技术栈 | Java/Spring + MySQL + Redis（与 PDM/P2P 的 Node22+TS+PostgreSQL 不一致，运维双心智） | 与 PDM/P2P 完全统一（Node22+TS+PostgreSQL），一个心智 |
| 资产复用 | 复用不了 PDM/P2P 已验证组件 | 直接复用：agentLoop、kanban dispatch、particle repo、SSE 事件总线、LLM 降级+确认范式、output guard、PG+pgvector+AGE |
| 上游耦合 | 深度魔改后无法跟随 upstream release | 独立演进，无上游约束 |
| 初始成本 | 看着小，实际 = 方言迁移(约 210 处) + 语义重构 + 能力叠建 | 看着大，实际 = 骨架复用 + 业务模块按闭环优先级增量构建 |
| 终态纯度 | 「带 AI 功能的 CRM」 | 「按 AI 原生方法论长的平台」 |
| 业务功能 | 现成（BI/审批/RBAC/移动端） | 需自建（用 YAGNI 收敛到主闭环） |

### 2.3 关键论点

方案 1 的「已有业务功能」优势本质是**一次性的存量资产**；而「AI 原生平台」是**持续演进的资产**（事件驱动进化、反馈闭环、能力审计都是长期机制）。用短期存量换长期形态，不划算。

且**业务功能是标准闭环**（线索 → 客户 → 商机 → 报价 → 合同 → 订单 → 回款），从无到有按优先级逐模块建，成本远比想象低——PDM 的 IPD 复杂度远超 CRM 域，你已把它从零跑通，说明团队具备同构开发能力。

## 3. 推荐路径：方案 2 的三阶段执行

从无到有 ≠ 大爆炸式全量开发。建议三阶段：

### 阶段 1：底座 MVP（对齐 PDM 已验证骨架）
- PostgreSQL + pgvector + Apache AGE 单库底座（继承 PDM 的 `embedding <=> $qvec` 向量检索、粒子图结构）。
- 粒子底座 + 本体/向量写时构建（ai-ontology-vector-build）。
- agentLoop + kanban dispatch 编排（ai-multi-agent-orchestration）。
- 10 大能力的核心机制先接线（粒子/本体/上下文/记忆/编排/门户/反馈/审计）。

### 阶段 2：认知 + 智能体层
- 记忆三构件（粒子图 + 快照 + 事件/推理）。
- 上下文分层注入（ai-context-layering）。
- 销售域 Action 表面（ai-native-action-design）：线索/商机/报价/合同/订单/回款。
- LLM 降级 + 确认范式（从 P2P/PDM 已验证的 action-confirm 迁移）。
- SSE 事件总线 + 实时看板 + output guard。

### 阶段 3：业务闭环增量构建
- 主闭环按 线索 → 客户 → 商机 → 报价 → 合同 → 订单 → 回款 逐个模块增量落地。
- 每个 Task 一 commit。
- 门户页面由 `ai-portal-page-generation`（NL → 受控 Schema → 运行时渲染）按需生成，不人工复刻固定页面。

### 风险与缓解
- 唯一真风险：业务功能覆盖面。缓解：YAGNI 收敛到主闭环 + 门户生成按需长页面，不一次复刻 CordysCRM 全部业务域。

## 4. CordysCRM 值得借鉴清单（机制范式，非实现形态）

基于对 `backend/crm/src/main/java/cn/cordys` 的代码勘察。

### 4.1 动态模块化数据模型（借鉴价值最高）
代码证据：`system/service/ModuleService.java`、`ModuleFieldService.java`、`ModuleFieldExtService.java`；`form/`（`ExtCustomFormDataMapper`、`ExtCustomFormMapper`）；`common/resolver/field/DatasourceResolver.java`、`DatasourceMultipleResolver.java`。
借鉴点：**「模块 + 字段元模型 + 对象实例化」的运行时表单**。映射到 AI 原生 = 粒子的运行时形态（一种粒子类型 + 属性元模型 + 对象实例化），新业务对象按配置长出来而非写死 CRUD 表。借鉴其「元模型驱动对象模型」思想，而非它的模块化权限/字典实现。

### 4.2 审批流（approval）→ AI 原生 HITL 闸
代码证据：`approval/service/ApprovalFlowService.java`（流程定义）、`ApprovalInstanceService.java`（实例）、`ApprovalTodoService.java`（待办）、`ApprovalFlowLogService.java`（日志）、`approval/aspect`（注解化触发）、`approval/handler`（分派）。
借鉴点：**注解 + 切面把审批能力注到任意业务操作，流程/实例/待办/日志完整闭环**。映射到 AI 原生 = 关键写操作的**人机确认闸（HITL）**，对应 P2P/PDM 已验证的 action-confirm 范式：AI 不能私自放行关键 Action，人类待办 + 日志追踪。

### 4.3 搜索体系（search）→ 给 AI 上下文检索当权限骨架
代码证据：`search/service/BaseSearchService.java` + `advanced/` + `global/`；`system/service/UserViewService.java`（用户自定义视图）。
借鉴点：**全局搜索 + 高级搜索 + 用户视图/权限**的检索骨架。映射到 AI 原生 = 带权限的上下文检索边界（ai-context-layering 需要「在哪一层能检索什么、用户能看到什么」），比从零设计检索权限强。

### 4.4 组织与 RBAC（organization / role）
代码证据：`system/service/OrganizationUserService.java`、`RoleService.java`、`UserRoleService.java`；`organization_id` 贯穿全部业务表（grep 到 75 处）。
借鉴点：**组织隔离 + RBAC 骨架**。AI 原生 CRM 一旦有 Agent 代操作、向量检索，「组织边界的检索隔离」与「Agent 的 RBAC 授权」是安全底座。复用其已生产验证的骨架而非从零设计权限模型。

### 4.5 前端（Vue3 + Naive-UI / Vant）
代码证据：`frontend/packages/web`（Vue3 + Naive-UI）、`frontend/packages/mobile`（Vue3 + Vant）、`frontend/packages/lib-shared`。
**前端技术线路（已锁定）**：Vue3 + Naive-UI（web 端）/ Vant（移动端），复用其成熟后台 UI 组件作为前端底座；但页面本身应由 `ai-portal-page-generation` 按需生成，不复刻固定页面。

## 5. 明确「不借鉴」清单

1. **数据模型不借鉴**：它的模块化字段模型给「人配置表单」用，不是给「AI 主动写对象/构建本体」用；AI 侧用按 AI-* 设计的粒子模型 + 写时向量化。其 137 个 MySQL 方言 SQL 不改 PG 搬不过来。
2. **技术栈不借鉴**：Java/Spring + MySQL + Redis 与 PDM/P2P（Node22 + TS + PostgreSQL）不一致，且 MySQL 无法原生承载「本体 + 图 + 向量」三合一（对照 §6 能力矩阵）。
3. **固定页面/全部业务模块不借鉴**：页面由门户生成能力按需产出；业务流程用 YAGNI 收敛到主闭环，不一次复刻其十余个业务域。

### 5bis 深度借鉴清单（界面设置层 + 销售业务逻辑层，2026-08-24 深度勘察）

> 基于对 `frontend/packages/web/src/views`（13 页面模块）与后端 `clue/opportunity/contract` 业务域（JPA 实体）的逐项检查。**核心发现：CordysCRM 的深度价值不在页面，而在「可配置化的业务机制」——这些正是 AI 原生平台要「原生内建」的机制。**

#### A. 界面设置层（4 点，门户生成的配置界面参照）

1. **动态表单配置抽屉（customFormConfigDrawer + memberPermissionTab）** → `ai-particle-system-design` 属性元模型的 UI 呈现。「配置表单字段 → 实时渲染 → 成员权限分栏」的抽屉式配置界面；AI 原生平台「按配置长对象」需要这套对象属性元模型的管理界面。
2. **用户视图配置（sys_user_view + UserViewCondition）** → `ai-context-layering` 的视图层实现。「用户自定义视图 = 资源类型 + 条件集（AND/OR）+ 固定视图 + 启用」，对应 Skills 的 `viewId:SELF`；AI 上下文注入可直接复用「视图 = 可配置过滤器」模型。
3. **数据脱敏配置（desensitizationModal）** → output guard 的安全闸。字段级脱敏配置界面；AI 让 Agent 代查代输出时脱敏是刚需（对应 Skills 安全红线「禁止暴露密钥/脱敏」）。
4. **容量/池配置抽屉（capacitySetDrawer / addOrEditPoolDrawer）** → 资源配额界面。线索池/公海的容量配额 + 池配置界面，配合后端领取/回收规则构成完整「共享资源池」管理界面。

#### B. 销售业务逻辑层（4 点，价值最高，AI 原生应原生内建）

5. **商机阶段配置 + 赢率 + 回退控制（opportunity_stage_config）** → 销售漏斗的「可配置状态机」。字段实证：name（阶段名）+ type + rate（赢率）+ afootRollBack（进行中回退）+ endRollBack（完结回退）+ pos（顺序）。**每个阶段可配赢率（预测量）、可配是否允许回退（防作弊/误操作，对应 Skills business-rules「商机只能向前」）**——商机粒子状态机应原生采用「阶段 + 赢率 + 回退控制」模型，让 funnel-engine 直接可算。
6. **线索池领取/回收规则（clue_pool_pick_rule / clue_pool_recycle_rule）** → 「公海」的自动化。字段实证：PickRule（限每日领取数量 + 限前归属人领取 + 领取间隔 + 限新数据）、RecycleRule（operator + condition 可配置回收条件）。**「超期未跟进自动回收」= 主动预警机制来源（risk-engine「超期未跟进」）**——池模型（领用规则 + 回收规则）既是业务（公海）也是预警触发源。
7. **商机/合同规则引擎（opportunity_rule + business-rules）** → 可配置业务规则。字段实证：scope（范围）+ operator（操作符）+ condition（条件）+ auto（自动回收）+ enable。**「范围 + 条件 + 动作」的可配置规则引擎 = AI 写操作护栏（action-confirm/HITL 的规则前置）**——AI 写操作前自动过规则层，不硬编码。
8. **回款计划 + 回款记录 + 发票 + 工商抬头（contract_payment_plan / record / invoice / business_title）** → L2C 收尾的财务闭环。字段实证：ContractPaymentPlan（planAmount 计划金额 + planEndTime 计划回款时间 + planStatus），ContractStageConfig（afootRollBack/endRollBack/流通类型 NORMAL-ADVANCED）。**「计划（应回）→ 记录（实回）→ 逾期判断（计划时间 vs 实际）」= 回款逾期预警（risk-engine「回款逾期」）判定依据**——回款粒子应原生承载「计划/记录/发票/抬头」结构。

#### C. 补充勘察（第二轮，2026-08-24 晚）：审批流设计器 + 安全底座 + 跟进/产品/工作台

> 本轮的**关键价值**：把「审批流设计器」从界面层提升到**可配置审批域的完整模型**；把「安全底座」拆出**文件级鉴权（F_A_TOKEN 双通道）**；把「跟进」「产品」两个域升级为**完整的业务对象模型**（计划→记录转化 + 产品→价格→报价关联）。

9. **审批流设计器（frontend `system/process/process/components`：addProcessDrawer + approval-flow + moreSetting + approval-node）** → 审批流可视化设计（HITL 界面侧）。
    - 实证：`approval-node/tabs/` 五个配置 Tab——`approverSettingTab`（审批人）/ `formPermissionTab`（表单字段权限）/ `afterApprovalTab`（审批后动作）/ `approvalLevelExamplePopover`（多级示例）/ `approvalMemberSelector`（成员选择）；`flow/` 含 `conditionDescription.ts` / `transform.ts` / `validation.ts`（画布数据的条件描述/变换/校验）；`setConditionDrawer.vue`（条件分支配置抽屉）。
    - 与后端 `ApprovalNodeApprover` 字段**一一对应**（grep 实证）：`approvalType`（MANUAL/AUTO_PASS/AUTO_REJECT——人工/自动通过/自动驳回）+ `multiApproverMode`（ALL/ANY/SEQUENTIAL——会签/或签/顺序签）+ `emptyApproverAction`（审批人为空：AUTO_PASS/ASSIGN_SPECIFIC 指定兜底/ASSIGN_ADMIN 转管理员）+ `sameSubmitterAction`（审批人与提交人相同：ALLOW/ASSIGN_SUPERIOR 转上级）+ `approverType`（MEMBER/SUPERIOR/MULTIPLE_SUPERIOR/DEPT_HEAD/MULTIPLE_DEPT_HEAD/ROLE）+ `approverDirection`（BOTTOM_UP/TOP_DOWN）+ `ccType`/`ccDirection`/`ccList`（抄送人）+ `passPostConfig`/`rejectPostConfig`（通过/驳回后动作）+ `fieldPermissions`（字段权限 JSON 配置）。
    - **转化**：这套「节点 + 条件分支 + 审批人/抄送/兜底 + 通过/驳回动作 + 字段权限」是审批流的**完整状态机模型**——AI 原生 HITL 闸应原生承载「节点拓扑（START/APPROVER/CONDITION/DEFAULT/END）+ 分支条件 + 审批人规则 + 兜底/自审规则 + 前后动作 + 字段权限」六要素，而非硬编码审批链。

10. **安全底座（framework `security/`：ShiroFilter + SessionUser + FileAccessAuthFilter + FileAccessTokenUtils）→ 会话/文件访问鉴权，含 API Key 双通道**。
    - 实证：`ShiroFilter.loadBaseFilterChain()` 链式 URL 规则（静态资源 anon → 认证路径 anon → **附件预览 `attachmentAuth` 过滤器**）；`FileAccessTokenUtils` 用 **F_A_TOKEN Cookie（AES 加密 sessionId）** 生成/校验/移除文件访问令牌（`generateToken`/`validateToken`/`setAccessCookie`/`deleteAccessCookie`）；`SessionUser` 含 **CSRF Token + sessionId**（`fromUser` 用 AES 加密 userId+随机串+时间戳）；`ApiKeyFilter` 支持 **API Key 认证**（`ApiKeyHandler.isApiKeyCall` → `UsernamePasswordToken(userId, NO_PASSWORD)` → 请求后 logout）——这是 Cordys 对外技能的**凭据通道**（对应 Skills 三参数）。
    - **转化**：①文件级鉴权（F_A_TOKEN 短令牌 + 预览路径独立过滤器）→ AI 原生「Agent 代取附件」的**文件级访问控制**，纳入 output guard + 权限层；②ApiKeyFilter 双通道 = §6.4 免登录直连的**工程化实证**（短期令牌替代密码会话，请求结束即注销）——我们可映射为 OAuth2/JWT 短期令牌 + 每个请求独立鉴权；③SessionUser 的 CSRF Token = 写操作防伪造（对应 action-confirm 前的 CSRF 校验）。

11. **跟进域（follow：FollowUpPlan → FollowUpRecord → Comment → CommentMention @提及）** → 跟进/协作完整对象模型。
    - 实证：`FollowUpPlan`（customerId/opportunityId/clueId + owner 负责人 + contactId 联系人 + estimatedTime 预计时间 + **method 跟进方式** + status 状态 PREPARED/UNDERWAY/COMPLETED/CANCELLED + **converted 是否转为跟进记录** + commentCount）；`FollowUpPlanType` 枚举 = **CUSTOMER / CLUE**（跟进对象两类）；`FollowUpPlanService` 的 `cancelPlan`/`updateStatus` 明写「**已完成且已转化的计划不允许取消/不允许改状态**」防御逻辑（`FollowUpPlanService.java:348`/`:391`）——计划状态机的**终态保护**。
    - `Comment`（resourceId + parentId 顶层评论 + replyToUserId 被回复人 + content + organizationId）→ 评论支持**多级回复**；`CommentMention`（commentId + userId）→ **@提及**绑定；`FollowUpPlanComment`/`FollowUpPlanCommentMention` 分别继承 Comment/CommentMention（多态子表）。
    - **转化**：跟进粒子应原生承载「**计划→记录 两态转化（converted 标记 + 终态保护）** + 评论多级回复（parentId 树） + @提及（跨角色协作提醒）」，并支持 CUSTOMER/CLUE/OPPORTUNITY 多对象绑定——这是销售协作闭环（对应 Skills lead「跟进状态/创建跟进记录/跟进计划」）的完整对象模型，且**计划状态机的终态保护**可直接迁移为 AI 写操作护栏（状态机合法流转校验）。

12. **产品域（product：Product + ProductPrice + 报价单关联）** → 报价的定价基础（产品→价格→报价 三级关联）。
    - 实证：`Product`（name + **price 单价（@DecimalMin/@DecimalMax 校验）** + status + pos）；`ProductPrice` 价格表（name + status + pos）+ `ProductPriceField` 自定义属性（BaseResourceSubField 动态字段）；`OpportunityQuotationAddRequest.java:40` 报价单子表 **`List<Map<String,Object>> products`**（报价单内嵌产品明细，`opportunity/service/OpportunityQuotationService.java:156` 写入 `moduleFields.add(new BaseModuleFieldValue("products", request.getProducts()))` + `:162` 保存表单配置快照）+ `OpportunityQuotation`（name + opportunityId + untilTime 有效期 + amount 累计金额 + approvalStatus 审核状态 + invalid 作废标记 + approved 是否审批通过过）。
    - **转化**：产品→价格表→报价单 三级定价模型应原生内建——**报价单 = 产品明细子表（多行产品 × 价格）+ 累计金额 + 有效期 + 审核状态**；且报价单已接入 `@HitApproval(formKey = FormKey.QUOTATION, executeType = CREATE)` 审批（`OpportunityQuotationService.java:132`）——**报价单是审批流模型的第一个直接落点**，对应角色商务/财务的「合同·报价审核」链路。

#### D. 一句话总结

**界面设置层（动态表单配置抽屉/视图配置/脱敏/容量池/审批流设计器）= 门户生成（ai-portal-page-generation）的配置界面参照；销售业务逻辑层（阶段-赢率-回退 / 池领取-回收规则 / 范围-条件规则引擎 / 回款计划-记录闭环 / 跟进计划-记录-评论 / 产品-价格）= AI 原生要「原生内建」的机制（状态机/规则引擎/生命周期/财务闭环/协作闭环/定价基础）。** 这些比从零设计更贴近销售真实业务，应作为阶段 3 业务闭环的机制输入。

21. **审批流 = 可配置一等公民（覆盖四大核心单据模块）** → HITL 闸的「流程化」实证。

22. **审批流四类配置项（= 审批流引擎的规则模型实证）**：
    - **①条件分支自定义**：按表单字段设置分流规则——「报价单金额＞10 万自动触发多级上级审批，其他情况直接走部门负责人审批」→ **规则引擎（scope + operator + condition + action，§5bis 借鉴点 7）在审批流中的应用**——不同场景流程无需重复搭建；
    - **②审批模式自定义**：连续多级上级、指定负责人等审批人设置；**会签（ALL）/或签（ANY）/依次审批（SEQUENTIAL）**多种模式；配置**审批异常自动通过**规则（对应 ApprovalNodeApprover.emptyApproverAction AUTO_PASS）；特殊场景顺畅流转；
    - **③表单权限自定义**：按审批节点对表单字段设置**隐藏/查看/编辑**三种权限（对应 ApprovalNodeApprover.fieldPermissions + formPermissionTab 前端 Tab）——**敏感数据按需隐藏 = 数据脱敏在审批节点的应用**（§5bis 借鉴点 3 联动）；
    - **④审批后操作自定义**：对不同审批结果设置**自动更新操作**（对应 passPostConfig/rejectPostConfig）——减少人工干预。
    - **转化**：审批流引擎的规则模型 = 「**条件分支（金额阈值路由）+ 审批人规则（会签/或签/依次 + 自动通过兜底）+ 表单字段权限（隐藏/查看/编辑）+ 结果后动作（自动更新）**」四层——正是我们 HITL 闸的**规则 Schema 实证**（对应 §6.3bis rules/ + write-engine）。

23. **审批节点权限控制（状态 × 操作矩阵）+ 审批记录（数字档案）** → HITL 的状态机 + 审计实证。
    - 节点权限 = **流程状态（已通过/审批中/已驳回/已撤销/待提交） × 操作（查看/编辑/删除/下载/作废）** 矩阵，操作权限一目了然，杜绝流程风险；支持审批人**批量处理、撤回、加签**，可设**自动审批规则**（同一审批人重复出现时仅首个节点审批，后续自动同意）；
    - 审批记录 = 每次提交/审批/意见完整记录，成为**业务合规的「数字档案」**：审批人操作时间、审批状态、审批意见全程可追溯；**审批附件与审批记录绑定存档**（财务核对/法务复盘直接查依据）；**抄送人按需查看审批记录**。
    - **转化**：①「状态 × 操作」矩阵 = 审批粒子的**状态机模型**（ApprovalInstance 状态 × 可执行操作白名单，删除类操作在审批态被禁——呼应「绝对禁止删除」红线）；②审批记录 + 附件绑定 = **审批审计事件流**（ai-capability-audit 输入，§4.2 借鉴点 2 的日志闭环升格为「数字档案」）；③**抄送人可查** = 审批的**跨角色可见性**（对应角色矩阵 ccType/ccList）。

24. **首页「我的待办」工作台（审批集中管理）** → 「对话即门户」的**任务聚合实证**。
    - 四大视图：**待我审批**（按报价/合同/订单/发票业务类型分类展示）/ **我处理的**（参与审批的进度查询）/ **我发起的**（实时追踪审批节点动态，无需反复催问）/ **抄送我的**（关键业务动态集中展示）；支持**一键勾选批量同意/驳回**。
    - **转化**：①我的待办 = **门户工作台（ai-portal-page-generation）的第一个「默认页」**——按业务类型分类 + 四视角（待我/我处理/我发起/抄送我）= 角色视图的**待办聚合**实证；②「批量同意/驳回」= 审批人的**批量操作 Action**（对应多智能体编排的批量派发）；③「我发起的实时追节点」= 审批流程的**可见性/追踪性**（对应 SSE 事件总线 + 看板的审批域事件）。

25. **功能优化/安全修复实证（工程化细节）**：
    - 合同模块增加**合同阶段看板模式**、订单模块增加**订单状态看板模式** → **看板视图（kanban）应用到业务对象**（对应多智能体编排的 kanban dispatch + 门户看板生成——业务对象的阶段/状态看板是门户生成的标准视图形态）；
    - **全量导出数据性能优化**、**初始化表单视图优化** → 批量导出 + 表单初始化的工程性能实证；
    - **Bug/安全修复**：产品详情删除附件未校验权限（#2429）→ **附件删除权限校验**（文件级鉴权 §5bis C-10 的删除侧）；合同收到回款后未展示回款记录（#2102）→ 回款记录聚合视图联动；商机表单显隐规则未生效（#2128）→ 表单显隐规则引擎；**部分接口 XSS 安全漏洞（#2239）+ 查询排序字段 SQL 注入漏洞** → **安全红线实证**（外部提交输入必须净化 + 查询参数化——对应 output guard 与 SQL 参数化，AI 原生平台从第一行代码就要防注入）。

**一句话**：v1.7.0 发布实证把审批流从「机制级」升级为「**成品级**」——**审批流引擎 = 条件分支（金额阈值路由）+ 审批人规则（会签/或签/依次 + 自动通过兜底）+ 表单字段权限（隐藏/查看/编辑）+ 结果后动作（自动更新）** 四层规则模型（覆盖报价/合同/发票/订单四模块），**「状态 × 操作」矩阵 + 审批记录（数字档案）** = 审批粒子的状态机 + 审计事件流，**「我的待办」工作台** = 门户默认页（四视角待办聚合 + 批量审批 + 节点追踪），**看板模式（合同阶段/订单状态）** = 业务对象看板视图实证；**XSS/SQL 注入修复 = 平台安全红线实证**（输入净化 + 参数化查询，AI 写操作与外部接入的第一原则）。全部纳入阶段 2 HITL / 阶段 3 审批粒子的设计输入。

#### H. v1.8.0 发布实证（移动端审批 + 导入 upsert 双模式 + 审批流能力继续补齐，2026-08-24 晚勘）

> 来源：Cordys CRM 官方发布说明《Cordys CRM发布v1.8.0版本》（2026-07-24）。本篇把 **PC 审批流扩展为全端（移动端审批）**，同时首次实证 **「导入新建/导入更新」双模式（upsert）** 与 **审批流数据回滚机制**——两个新机制都直接对应 AI 原生平台的核心：批量写入（upsert = 写粒子原子性）与写后回调补偿（回滚 = 事务补偿）。**关键价值：审批流从 PC 单端变成移动端随时随地（移动端我的待办 + 就地审批 + 加签/退回），导入从「一次性新增」升级为「upsert（按系统唯一 ID 匹配更新）」，审批流新增「数据回滚机制」——两者都是写操作的工程化实证（upsert 幂等 + 回滚补偿）。**

26. **移动端审批（移动端首页「我的待办」+ 就地审批）** → 审批流的「全端可达」实证。

27. **导入 upsert 双模式（导入新建 / 导入更新）** → 批量写粒子的「幂等 upsert」实证。
    - **导入新建**：上传 Excel 模板 → 表格数据识别为全新线索 → **直接新增至线索池**（外部渠道线索批量入库）；
    - **导入更新**（重要新增）：**依托系统唯一 ID 作为匹配依据** → 上传含线索唯一 ID 的 Excel → **自动精准匹配系统内存量线索** → 匹配成功后**用表格最新信息覆盖更新对应线索字段**（大批量线索统一修正与信息同步）；同一机制扩展到**发票导入、回款计划/回款记录导入**（合同模块）+ **公海、线索池新增导入功能**；导出功能同步**支持导出系统唯一 ID**（为导入更新提供匹配键闭环）。
    - **转化**：①「**导入更新 = 按唯一 ID 匹配的 upsert（幂等批量写）**」= **批量写粒子的原生产物**（upsert 语义：存在则更新、不存在则新增，AI 批量写 Action 的工程实证——对应 crm-lead 的批量导入 Action + `ai-native-action-design` 的写动作表面）；②「**导出含唯一 ID**」= **ID 导出闭环**（导入更新的匹配键来源——导出/导入互为镜像）；③「导入新建 → 新增至线索池」= **外部渠道批量入池**（对应 §5bis E-16 标讯引线索的批量侧，线索池 = 共享资源池的批量写入实证）。

    - **转化**：①**数据回滚 = 审批粒子的补偿（compensation）机制实证**——「写前快照 + 驳回/失败回滚」= `ai-native-action-design` 写 Action 的**事务完整性**（对账核销等聚合视图联动，呼应 §5bis F-19 发票对账核销）；②**审批抄送通知** = 主动预警的**通知通道扩展**（审批动态 → 抄送人，对应角色矩阵 ccType/ccList + §6.3ter 主动预警）；③**审批字段可编辑性** = 审批流配置的**可扩展性**（审批流引擎持续可编辑，非静态定义）。

29. **功能优化/问题修复实证（表单/导入/选择器/看板）** → 门户与导入组件的工程细节。
    - **子表格支持添加更多基础字段**（#2834）→ 动态表单子表格可扩展性（§5bis A-1 动态表单配置抽屉的明细行扩展）；

### 5ter.1 线索与线索池（clue / lead pool）

**业务事实**（代码库 + v1.8.0 实证）：
- 线索对象字段：线索基础信息 + 跟进状态 + 归属人 + 创建时间 + 来源 + 行业 + 联系人（职能/电话/邮件）。
- **线索池（共享线索）**：多条线索可进入一个池共享；**领取规则**（CluePoolPickRule）：限定每日领取数量 + 限定前归属人领取 + 领取间隔 + 限定新数据；**回收规则**（CluePoolRecycleRule）：operator + condition 可配置回收条件（如「超期未跟进自动回收」）。
- **线索转化**：线索 → 客户（跳转链路）、线索 → 商机；转化后线索状态变更。
- **导入两种模式**（v1.8.0）：导入新建（Excel → 新线索 → 入线索池）+ 导入更新（按系统唯一 ID 匹配存量线索 → 覆盖更新字段）。
- **线索移入线索池可指定目标池**（#2693），非只有一个池。

### 5ter.2 客户与公海（customer / account pool）

**业务事实**（代码库 + v1.5.0/v1.8.0 实证）：
- 客户对象字段：客户档案 + 联系人（多联系人）+ 跟进记录 + 客户 360 关联视图。
- **公海（共享客户）**：客户可进入公海共享；**客户移入公海可指定公海**（#2879/#2682）。
- **工商抬头管理**（v1.5.0）：录入/核验客户完整工商抬头、统一社会信用代码、注册地址、法定代表人；**联动企查查/爱企查第三方平台自动同步与校验**。
- **深度客户画像**（v1.8.0 Skills）：客户 + 关联联系人（职能/电话/邮件）+ 商机 + 跟进记录跨模块聚合。

### 5ter.3 商机与商机阶段（opportunity / stage config）

**业务事实**（代码库实证）：
- 商机对象关联：客户 + 产品 + 报价单 + 跟进。
- **商机阶段配置**（OpportunityStageConfig）：阶段名 + 类型 + **赢率** + 进行中回退（afootRollBack）+ 完结回退（endRollBack）+ 顺序（pos）——「商机只能向前推进，不能回退（除非管理员）」（business-rules 实证）。
- **统计维度**（v1.4.0/v1.5.0）：商机数据分析按阶段分组；赢单商机「预计结束时间/实际结束时间」对比。
- **商机规则引擎**（OpportunityRule）：scope（范围）+ operator（操作符）+ condition（条件）+ auto（自动）+ enable——可配置商机业务规则（如金额阈值自动预警）。

### 5ter.4 产品与价格表（product / price list）

**业务事实**（代码库 + v1.4.0 实证）：
- **产品对象**：产品名称 + 单价（带范围校验）+ 状态 + 排序。
- **价格表**（v1.4.0）：同一产品多套定价（适配不同客户/业务场景）；**价格有效期** + **价格权限管控** + **价格变更日志**；价格表关联产品**自动同步价格**；价格表可配置产品规格/折扣。
- **定价链路**：产品 → 价格表（多套定价）→ 报价单（自动取价 + 金额计算）→ 合同。

### 5ter.5 报价单（quotation）

**业务事实**（v1.4.0/v1.7.0 实证）：
- 报价单 = **商机下二级资源**；创建时**选择产品 + 价格表** → 系统按**金额计算规则自动算金额**（定价 × 折扣 × 税点运算符组合）。
- 报价单字段：名称 + 商机 + 有效期至 + 累计金额 + 审核状态 + 是否作废 + 是否审批通过过。
- **报价单内嵌产品明细**（OpportunityQuotationAddRequest）：`products` 子表（多行产品 × 数量价格）；可含**多个产品表格**（v1.7.0）。
- **报价单审批**（v1.4.0/v1.7.0）：内置审批流程（提交 → 审批 → 通过可下载）；报价单可关联商机与合同（商机详情可查看全部报价单）。
- **报价表单可配置**：系统→模块配置→报价单表单设置（必填项、字段权限、**关联价格表**、**金额计算规则**两个特殊设置项）。

### 5ter.6 合同（contract）

**业务事实**（v1.4.0/v1.5.0/v1.7.0 实证）：
- 合同 = **独立业务对象**（关联报价单/商机，销售信息自动同步）；合同表单可自定义配置。
- **合同审批**：内置审批流程（提交 → 有权限用户审批 → 结果按消息通知方式回传）；合同模块覆盖四大审批流模块之一。
- **合同阶段看板模式**（v1.7.0）：合同按阶段看板展示。
- **合同相关通知**（v1.7.0）：新增合同通知。
- 合同域二级资源：**回款计划** + **回款记录** + **工商抬头** + **发票**（v1.4.0/v1.5.0/v1.8.0）。

### 5ter.7 回款计划与回款记录（payment plan / payment record）

**业务事实**（v1.4.0/v1.5.0 实证）：
- **回款计划**（v1.4.0）：合同模块下创建/查看回款计划；未来回款模块认款后**计划状态自动更新**。
- **回款记录**（v1.5.0）：录入每笔回款金额/时间/关联合同；**自动关联客户、合同、订单**；实时追踪回款进度、**留存凭证**、降低坏账风险。
- **计划 vs 记录对账**：合同详情可查全部回款记录；「应回（计划）vs 实回（记录）」差额/逾期分析。

### 5ter.8 发票（invoice）

**业务事实**（v1.5.0/v1.7.0 实证）：
- **发票记录**：发票类型/号码/开票金额/开票日期/对应客户合同订单 + 电子附件上传。
- **自动关联工商抬头与回款数据**：方便**对账核销**，减少开票差错、降低重复开票。
- **发票审批**（v1.7.0）：发票为四大审批流模块之一。
- 发票域：合同详情可查全部发票开具记录（发票 = 合同二级资源）。

### 5ter.9 订单（order）

**业务事实**（v1.7.0 实证）：
- 订单（order）为独立业务对象：订单审批（四大审批流模块之一）+ **订单状态看板模式**。
- 订单与回款记录、发票的关联（回款记录关联订单）。

### 5ter.10 跟进（follow：计划/记录/评论/@提及）

**业务事实**（代码库实证）：
- **跟进计划**（FollowUpPlan）：客户/商机/线索三对象绑定 + 负责人 + 联系人 + 预计时间 + 跟进方式 + 状态（待开始/进行中/已完成/已取消）+ **是否转为跟进记录（converted）** + 评论数。
- **跟进记录**（FollowUpRecord）：客户/商机/线索 + 跟进内容 + 跟进时间 + 跟进方式 + 负责人 + 联系人。
- **计划→记录转化 + 终态保护**（FollowUpPlanService）：「已完成且已转化的计划不允许取消/不允许改状态」。
- **评论**（Comment）：资源绑定 + 顶层评论（parentId 树）+ 被回复人 + 内容；**@提及**（CommentMention）：评论绑定被提及用户。
- 跟进计划/记录的评论可多级回复（parentId），@提及 = 跨角色协作提醒。

### 5ter.11 审批流（approval flow）——最重要的业务机制

**业务事实**（代码库 + v1.7.0/v1.8.0 实证）：
- **覆盖模块**：报价、合同、发票、订单四大业务单据（v1.7.0）。
- **审批流结构**（代码库）：审批流（flow，可配置 + 启停 + 提交人撤回/批量处理/加签）→ 审批流版本（version）→ 审批节点（node：START/APPROVER/CONDITION/DEFAULT/END）→ 节点审批人（approver）→ 节点条件（condition）→ 节点连线（link）。
- **审批节点配置**（ApprovalNodeApprover）：审批类型（人工/自动通过/自动驳回）+ 多人审批方式（会签 ALL/或签 ANY/依次 SEQUENTIAL）+ 审批人为空动作（自动通过/指定兜底/转管理员）+ 审批人与提交人相同动作（允许/转上级）+ 审批人类型（成员/上级/多级上级/部门负责人/多级部门负责人/角色）+ 审批人方向（自下而上/自上而下）+ 抄送人（类型/方向/列表）+ 通过后配置 + 驳回后配置 + 字段权限。
- **审批流四类配置项**（v1.7.0）：条件分支自定义（按表单字段分流，如报价金额＞10万自动多级上级审批 vs 部门负责人）+ 审批模式自定义 + 表单权限自定义（按节点对字段隐藏/查看/编辑）+ 审批后操作自定义（结果自动更新）。
- **审批节点权限控制**（v1.7.0）：流程状态（已通过/审批中/已驳回/已撤销/待提交）× 操作（查看/编辑/删除/下载/作废）矩阵；批量处理/撤回/加签；自动审批规则（同一审批人仅首个节点审批，后续自动同意）。
- **审批记录**（v1.7.0）：每次提交/审批/意见完整记录（数字档案）+ 审批附件绑定存档 + 抄送人可查。
- **我的待办工作台**（v1.7.0 PC / v1.8.0 移动端）：待我审批（按单据类型分类）/ 我处理的 / 我发起的（实时追踪节点）/ 抄送我的 + 一键批量同意/驳回 + **审批意见/附件上传 + 就地审批（移动端详情页直接同意/驳回/加签/退回）**。
- **数据回滚机制**（v1.8.0）：审批结果触发的数据变更可回滚。

### 5ter.12 标讯与外部数据源（tender / external data）

**业务事实**（v1.4.0/v1.5.0 实证）：

### 5ter.13 安全底座（security）

**业务事实**（代码库实证）：
- **过滤器链**（ShiroFilter）：静态资源 anon → 认证路径 anon → **附件预览 attachmentAuth**（文件访问 Filter）。
- **文件访问令牌**（FileAccessTokenUtils）：F_A_TOKEN Cookie（AES 加密 sessionId）生成/校验/设置/移除；HttpOnly + Secure。
- **会话用户**（SessionUser）：CSRF Token + sessionId（AES + 随机串 + 时间戳）。
- **API Key 双通道**（ApiKeyFilter）：API Key 请求免账号密码登录（UsernamePasswordToken(userId, NO_PASSWORD)），请求结束后 logout。
- **安全红线**（Skills SKILL.md）：绝对禁止删除；禁止暴露密钥值（脱敏）；错误消息含密钥必须脱敏。
- **安全修复实证**（v1.7.0/v1.5.0）：XSS 漏洞修复、SQL 注入修复、附件删除权限校验（#2429）、高级搜索按联系人权限不正确（#688）。

### 5ter.17 定价链路与金额计算（pricing / amount calculation）

## 5quater 行业垂直场景与销售方法论吸收（印刷行业 + B2B 决策逻辑，领域知识输入，2026-08-26）

### 5quater.0 全景速览与定位

两个新增领域输入源（位于 `doc/` 目录，与 §5ter 的 CordysCRM 源**正交**）：

- **源 A：印刷行业销售管理核心痛点**（8 项痛点 + 3 项衍生困境）。代表一个**高定制、重成本、强交付约束**的 B2B 垂直行业样本——其痛点对 CRM 的「报价智能 / 毛利实时 / 交期产能协同 / 非标参数化」提出远高于通用 CRM 的要求。
- **源 B：2B 销售全流程关键决策、输入信息、决策逻辑**（7 阶段 × 决策/输入/方法 + 5 类高频输入 + 6 方法论）。代表**销售方法论本体**——把「销售怎么做出正确决策」结构化，是 AI 原生平台「辅助决策」能力的直接需求来源。

**与 §5ter 的关系（正交，非重复）**：
- §5ter = 功能存在性（有没有这个对象/字段/流程/界面）。
- §5quater = 行业实例化 + 决策智能性（这个行业怎么卖、销售怎么决策、平台怎么辅助做对）。
- 二者共同构成阶段 1-3 的**完整业务设计输入**：§5ter 告诉你「建什么」，§5quater 告诉你「建出来怎么帮销售赢单」。

**吸收基线原则（与 §5ter 一致）**：先全面理解行业与方法论，暂不做 AI 原生转化；后续每个业务模块的设计必须能覆盖 §5quater 每个能力点（覆盖 = 可回答「我们如何支撑这个行业场景 / 这个决策」）。

### 5quater.6 理念增强点（E1-E6，与 §5ter 的 D1-D12 互补，非冲突）

§5ter 的 D1-D12 是「平台形态差异」（外层封装 vs 原生内建）；§5quater 暴露的是「行业/方法论对能力的**增强要求**」——这些在通用 CRM 里是可选模块，在印刷 B2B 里是**刚需**：

- **E1 报价智能（P1）**：通用 CRM 报价=填数字；印刷 B2B 要求「结构化工艺参数 + 自动损耗 + 历史复用 + 成本 BOM」，是 ai-native-action-design 金额写时计算管线的**行业强化版**。
- **E2 实时毛利（P3）**：通用 CRM 利润=事后报表；印刷要求「接单时预判 + 忙季不赚钱预警」，把 ai-feedback-loop 从「对账」前移到「接单决策」。
- **E3 交期产能协同（P4）**：把 ai-event-driven-evolution 的「预警」扩展到「产能事件源」——交期承诺不是销售拍板，而是产能事件校验。
- **E4 角色地图决策（源 B 阶段二）**：把 ai-context-layering 的「角色=上下文」从「查询偏好」升级为「决策链情报」（Coach/否决点/建议权 vs 拍板权），是 L4 治理决策层的**销售方法论实例化**。
- **E5 止损与事实vs话术（源 B 阶段五/六方法论）**：把 ai-event-driven-evolution 的「预警」与 ai-memory-lifecycle 的「记忆」绑定到销售动作——时间节点未推进→止损事件；多方信息交叉验证→Coach 情报优先。
- **E6 非标参数化（P7）**：把 ai-particle-system-design 的「粒子属性元模型」要求从「固定维度」提升到「行业自定义维度」（特殊色号/异形模切），验证粒子模型的**可扩展属性**能力。

> **设计输入结论**：§5quater 不新增能力（10 大能力清单固定不变），而是为 10 大能力提供**行业垂直 + 销售方法论的具体输入**，使阶段 2/3 的业务模块设计（尤其报价/商机/合同/回款/跟进）直接对齐印刷 B2B 的真实痛点与决策逻辑。这是 §7 待批准项第 12 条的基础。

## 6. 技术底座对照（为什么「跟 PDM 一样」成立）

| 能力 | MySQL+Redis（CordysCRM 现状） | PostgreSQL+pgvector+AGE（PDM 同款） |
|---|---|---|
| 本体/知识图谱 | 不原生支持（无图引擎/推理） | Apache AGE：openCypher 图 + 本体建模 |
| 向量检索 | MySQL 8.0 原生无 VECTOR；Redis 需 RediSearch | pgvector：`embedding <=> $qvec`（PDM 已验证 `l2Retrieval.ts`） |
| 关系型事务 | 支持 | 支持（ACID） |
| AI 记忆/粒子 | 需外部挂接 | 单库原生承载 |

因此将技术底座换成 PDM 同款 = 统一到 **Node22 + TS + PostgreSQL（pgvector + AGE）**，业务与 AI 能力长在同一个库，运维一个心智。

### 6.1 Cordys CRM Skills = 阶段 2/3 的验收参照（外部印证）

飞致云将 Cordys CRM 核心操作封装为「Cordys CRM Skills」AI 技能模块，供办公智能体（如千问）以自然语言直接调用，无需登录 CRM 平台，并结合定时任务做周期性巡检与提醒。其四个核心能力与我们 10 大能力蓝图**逐项对应**，可作为阶段 2/3 的可验收目标：

| Cordys CRM Skills 能力 | 我们设计中的落点 | 所属能力/阶段 |
|---|---|---|
| **角色自适应**（自动识别角色：销售/经理/高管/商务/财务，切换数据范围/关注重点/输出风格） | 上下文分层的治理决策层 + RBAC 权限化检索（借鉴点 4.4） | `ai-context-layering`；阶段 2 |
| **自然语言交互**（日常语言提问/指令，无需学查询语法/字段名） | AI 对话门户 + 意图→Action 解析 | `ai-portal-page-generation` + `ai-native-action-design`；阶段 2 |
| **L2C 全链路覆盖**（线索→回款，查询/写入/转化/追踪） | 销售域 Action 表面 + 业务闭环增量 | `ai-native-action-design`；阶段 3 |

**额外论证**：
- Cordys CRM Skills 正是 CordysCRM「改造为 AI 原生」的官方尝试，但实现是**在 Java/MySQL 旧底座上外层叠加技能封装**，能力是「叠上去的」而非「长出来的」，恰好验证方案 1 的局限（语义不对齐、能力逆向套接）；方案 2 让这些能力**原生内建**（写时向量化、事件驱动进化、Action 表面原生）。
- 「角色自适应」的**数据范围 + 关注重点 + 输出风格**三要素，是 `ai-context-layering` 清晰的上下文分层实现目标，可直接作为阶段 2 验收判据。

### 6.2 借鉴点（重要）：角色/SKILL 的「平台抽象」机制

官方教程（2026-08-07，千问办公 x Cordys CRM Skills）展示了 Cordys CRM Skills 的完整结构：**「角色」与「SKILL」分离的平台抽象**——角色定义「谁、看什么、预警什么、怎么输出」，SKILL 定义「业务对象 × 操作能力」。这套抽象与我们的 10 大能力蓝图高度同构，值得转化借鉴：

**角色 × 四要素（数据范围 / 关注重点 / 主动预警 / 输出风格）：**

| 角色 | 核心关注 | 数据范围 | 主动预警 | 输出风格 |
|---|---|---|---|---|
| 销售 | 我接下来该做什么？ | 我的客户/线索/商机 | 超期未跟进、商机卡顿 | 优先级行动清单 |
| 经理 | 谁需要我关注？ | 全部门+子团队 | 跟进率低、转化骤降 | 团队看板（可下钻到个人） |
| 高管 | 公司销售目标达成如何？ | 全公司 | 目标缺口、部门偏离 | 趋势分析、对比、预测 |
| 商务 | 合同签对了吗？ | 合同+审批流 | 到期未续、审批卡顿 | 合同状态+到期预警 |
| 财务 | 钱到哪里了？ | 合同→回款→发票 | 逾期、未开票、链路断裂 | 应收全景、催收优先级排序 |

**SKILL 模块 × 业务对象（L2C 全链路）：**

| 模块 | 核心能力 | 典型示例 |
|---|---|---|
| lead | 线索查询、跟进状态 | “查询我名下本周新增的线索” |
| account | 客户档案、联系人、跟进记录 | “最近和某某客户有哪些跟进记录” |
| opportunity | 商机阶段、报价、预警 | “预警一下快要超期的商机” |
| contract | 合同状态、审批流、到期提醒（含回款计划/回款记录/工商抬头/发票二级资源） | “这笔合同审批到哪一步了” |
| lead-pool | 线索池（共享线索） | “线索池里最近新增了哪些线索” |
| account-pool | 公海（共享客户） | “公海里最近新增了哪些客户” |

**转化到我们平台的借鉴方式**（不是照搬，是抽象同构）：

1. **角色 = 上下文分层实例**：五种角色的「数据范围 / 关注重点 / 主动预警 / 输出风格」就是 `ai-context-layering` 的治理决策层实例化——角色不再是 UI 层面「人选的页面」，而是**上下文分层的注入配置**（L4 治理决策层）。这为阶段 2 提供了**可直接落地的验收样例**。
2. **SKILL = Action 表面的聚合分组**：六个模块（lead/account/opportunity/contract/lead-pool/account-pool）本质上就是按**业务对象**聚合的 Action 表面（`ai-native-action-design`），每个模块 = 「对象 + 查询/写入/转化/追踪」的标准能力集。这为阶段 3 的销售域 Action 表面提供了**精确的对象粒度参照**（线索/客户/商机/合同/回款池/公海）。
3. **角色↔SKILL 的绑定 = 权限化检索 + HITL 边界**：角色自动识别（基于 API 凭据）→ 数据范围 = 组织 RBAC（借鉴点 4.4）；写操作走审批/HITL（借鉴点 4.2）。这份「角色驱动上下文 + SKILL 操作」的绑定，正好落在「多智能体编排（角色→Agent）+ 门户生成（对话入口）」的交界——**这就是我们平台「对话即门户」的产品形态**。

**一句话判断**：**借鉴它「角色/技能分离的抽象定义」机制**，不借用它的实现（仍是 Java/MySQL 外层封装）；把「角色=上下文分层配置、SKILL=Action 表面聚合」转成我们平台的**原生抽象层**（阶段 2 落地角色分层、阶段 3 落地 SKILL 模块化 Action）。

### 6.3 如何分析并形成「哪些 SKILL」——五步推导法 + 候选清单

**核心原则：SKILL 不是拍脑袋列的，是从业务流程结构性推导出来的。**

1. **定义主业务链路（L2C）**：线索 → 客户 → 商机 → 报价 → 合同 → 订单 → 回款/发票。这条链路是 SKILL 清单的**骨架**。
2. **横切能力维度**：对每个业务对象问「对这个对象需要哪些操作？」——查询 / 创建 / 更新 / 转化 / 追踪 / 预警 / 分析（漏斗）。
3. **按业务对象分组**：SKILL 的**自然粒度 = 业务对象**。每个 SKILL 一个对象（线索、客户、商机、合同、回款…），内部聚合该对象全操作能力。这就是 Cordys 官方「模块 = 对象」的做法（§6.2）。
4. **展开为 Action 表面**：每个 SKILL 进一步拆成**可执行的 Action**（命名空间 + 动词），落地到 `ai-native-action-design`。例如 `crm-clue-create`、`crm-opp-convert`、`crm-contract-approve`。
5. **绑定角色**：把每个 SKILL 的**可见范围 / 预警 / 输出风格**绑定到角色（销售/经理/高管/商务/财务），落到 `ai-context-layering` 的治理决策层。

**推导出的候选 SKILL 清单（与 Cordys 官方对齐 + 我们平台扩展）：**

| 候选 SKILL | 业务对象 | 核心能力（操作维度） | 对应阶段 |
|---|---|---|---|
| crm-lead | 线索 | 查询、创建、分配、转化（→商机）、跟进状态 | 阶段 3 |
| crm-account | 客户 | 档案、联系人、跟进记录、客户 360 | 阶段 3 |
| crm-opportunity | 商机 | 阶段流转、报价、转化/丢单、预警 | 阶段 3 |
| crm-quote | 报价 | 创建、审批、转为合同 | 阶段 3 |
| crm-contract | 合同 | 状态、审批流、到期提醒、二级资源（回款计划/发票/工商抬头） | 阶段 3 |
| crm-order | 订单 | 创建、状态跟踪 | 阶段 3 |
| crm-payment | 回款/发票 | 回款记录、发票、逾期预警、催收优先级 | 阶段 3 |
| crm-lead-pool | 线索池 | 共享线索查询 | 阶段 3 |
| crm-account-pool | 公海 | 共享客户查询 | 阶段 3 |
| crm-funnel（分析类） | 全链路 | 漏斗分析、部门复盘、销售目标达成 | 阶段 2/3 |
| crm-alert（预警类） | 全链路 | 超期未跟进/商机卡顿/回款逾期/链路断裂 | 阶段 2/3 |

> 注：`crm-quote` / `crm-order` / `crm-funnel` / `crm-alert` 是基于我们主闭环的**扩展**——Cordys 官方把报价挂在商机下、订单未单列，但我们的主闭环（线索→客户→商机→报价→合同→订单→回款）需要它们独立成 skill。其余（lead/account/opportunity/contract/lead-pool/account-pool/payment）与官方对齐，形成「官方模块 = 我们 skill 清单」的精确映射。

**如何借鉴 Cordys CRM Skills（借鉴方法与边界）：**

| 借鉴什么 | 怎么借鉴 | 不借鉴什么 |
|---|---|---|
| 模块划分 = 按对象聚合 | 直接采用「每个 skill 一个业务对象 + 能力集」的分组方式 | 不借它的 API Key 凭据机制（我们改为 OAuth/JWT + 组织 RBAC） |
| 角色四要素（数据范围/关注重点/主动预警/输出风格） | 直接作为 `ai-context-layering` 角色注入配置的模板 | 不借它的「角色 = 人」单一模型（我们是「智能体 + 角色」双层） |
| 典型自然语言示例 | 作为「意图 → Action」解析的训练样本/验收用例（“查询我名下本周新增线索”） | 不借它的 NL 实现——它靠千问外部智能体理解，我们是**平台内建意图解析** |
| L2C 链路覆盖范围 | 作为我们阶段 3 的验收参照 | 不借它的 Java/MySQL 外层封装实现 |

**一句话**：**借鉴它的「推导方法 + 分组粒度 + 角色要素」**（这些是机制、可移植），**不借鉴它的「实现形态」**（API Key 驱动、外层封装、依赖外部智能体）——因为我们的平台是**原生内建**这些能力的（意图→Action、角色→上下文分层、对象→粒子/向量检索）。

### 6.3bis 官方第一手实现结构（GitHub 仓库实证，2026-08-24 核对）

> 参考来源：[1Panel-dev/CordysCRM-skills](https://github.com/1Panel-dev/CordysCRM-skills) `skills/cordys-crm` 目录（官方仓库，非猜测）。

官方 SKILL 的实现骨架由「SKILL.md + core/ + profiles/ + rules/ + scripts/ + .env.example」组成，**与我们的 10 大能力蓝图逐项对应**，是最佳实现参照：

**1. SKILL.md（技能定义 + 核心架构 + 安全红线）**
- 定义触发词（线索/客户/商机/跟进/报价单/合同/回款/发票/工商抬头/订单/审批/漏斗/管道/CRM）
- 环境变量：`CORDYS_CRM_DOMAIN` / `CORDYS_ACCESS_KEY` / `CORDYS_SECRET_KEY`（可选 `ROLE_MAP`）
- 安全红线（抄录，极有价值）：
  - `cordys raw`——只支持查询，不支持写入/删除/转化
  - **绝对禁止执行任何删除操作**
  - 禁止在输出中暴露任何密钥值；错误消息含密钥必须脱敏
- 核心架构（意图路由树）：单模块查询 / L2C 链路追踪（linkage-engine） / 漏斗分析（funnel-engine） / 模糊工作指令（intent-engine） / 写入操作（write-engine） / 审批意图（approval 命令族） / 角色适配（销售/经理/高管/商务/财务） / 输出（结论 + L2C 视图 + 预警 + 建议）
- **引擎按需加载策略**：`role-engine.md` 唯一启动必加载；其余按需加载避免 token 浪费——这是「上下文分层」的工程化实证！
- 输出原则（关键结论 → 核心数据 ≤5列 ≤10条 → L2C 链路视图 → 链路健康 → 异常提醒 → 建议动作）

**2. core/（引擎家族 = 我们的能力模块的「技能化」形态）**
| 文件 | 对应我们能力 | 作用 |
|---|---|---|
| role-engine.md | ai-context-layering 治理决策层 | 唯一必加载：角色匹配逻辑 |
| cli-spec.md / cli-reference.md | ai-native-action-design Action 表面 | 构造 `cordys.sh crm ...` 命令、字段类型、审批 JSON |
| output-engine.md | ai-feedback-loop 输出规范 | 格式化输出（表格 ≤5列，结论优先） |
| risk-engine.md | ai-event-driven-evolution 主动预警 | 扫描预警风险（销售预警/L2C 跨模块风险） |
| linkage-engine.md | L2C 链路追踪 | 跨模块关联追踪（Customer 360/链路断裂检测） |
| funnel-engine.md | 漏斗分析 | 多模块聚合（转化率/管道） |
| intent-engine.md | ai-portal-page-generation 意图→Action | **意图路由引擎**：模糊指令（"今天做什么/周报"）自动匹配工作流 |
| write-engine.md | ai-native-action-design + action-confirm | **写操作引擎**：创建/更新，结合 rules/ 做规则校验 |

**3. profiles/（角色 × 五要素，实证升级）**
- 五角色文件：`sales.md` / `sales-manager.md` / `executive.md` / `contract-admin.md`（商务）/ `finance.md`
- **每个角色不只是四要素，而是完整上下文配置**（七要素）：
  - **核心关注**（我的线索/商机/客户/今日计划/业绩/L2C 链路）
  - **默认查询偏好**（映射到具体 CLI 命令，如 `crm page lead '{"viewId":"SELF"}'`）
  - **L2C 典型工作流**（晨会速览 / 跟进优先级排序 / 客户深耕 / 周回顾 / 月度总结 / 链路回查）
  - **KPI 基准线**（指标 × 正常/警戒/严重三级，如线索首次跟进 ≤24h / 24-48h / >48h 🚨）
  - **跨角色协作**（触发条件 → 提醒谁做什么，如"商机赢单 → 提醒商务建合同 + 财务备回款"）
  - **权限边界**（能做 / 不能做，如销售"能查自己名下"、"不能查全公司漏斗"）
  - **角色内子类型**（新销售/老销售/售前顾问，可经 `ROLE_MAP` 建独立 profile）
- **这就是「角色 = 上下文分层配置」的最佳完整实例**：每个角色是一个可加载的上下文 profile，注入数据范围/关注/预警/输出/权限边界。

**4. rules/（写操作规则治理 = 我们 action-confirm + HITL 的补充机制）**
- 目录：`form-rules/{module}.md`（表单校验）、`field-mapping/*.md`（字段映射，如 lead→account）、`business-rules/{module}.md`（业务规则）
- **加载优先级**（实证）：API 表单定义（系统规则）→ form-rules（自定义校验）→ field-mapping → business-rules；**自定义增强但不覆盖系统规则，文件缺失静默跳过**
- `business-rules/opportunity.md` 实证：「商机阶段只能向前推进，不能回退（除非管理员）」「合同金额修改超 20% 需经理审批」「赢单不可回退、输单必须填原因」——**这正是 AI 写操作的业务规则闸**！
- 对我们直接借鉴：**AI 写操作前必须先过规则层**（form-rules 校验 + business-rules 约束 + 状态机合法流转），与 action-confirm 的「写前确认」结合 = 完整的 AI 写护栏。

**5. scripts/ + .env.example**：安装脚本与敏感环境文件（不提交版本控制）。

> **结论（强力佐证）**：官方 SKILL 的 `core/`（引擎家族）+ `profiles/`（角色配置）+ `rules/`（规则治理）+ SKILL.md（意图路由 + 安全红线）**就是「我们的 10 大能力蓝图」的技能化实现形态**。它证明：角色自适应 = 上下文分层 + role-engine；NL 交互 = intent-engine 意图路由；L2C 全链路 = linkage/funnel/write 引擎；主动预警 = risk-engine + KPI 基准线。**我们的方案 2 完全正确，且这次有了第一手的实现参照。**

- **对号入座**：一个技能包 **多市场发布**（GitHub 源仓库 + ClawHub + WorkBuddy 市场）= 我们技能目录（Skill Catalog）的标准形态——**源仓库托管 + 多市场分发**，任意办公智能体从其所在市场即可发现/安装（对应 §6.4 第 1 条 + 第 5 条统一技能协议，同一 skill 包跨市场一致消费）。

**2. 初始化配置流程（= §6.4 第 2/4 条免登录直连 + 角色识别的全流程实证）**
```
新建任务 → 选择 CordysCRM 技能 → 发送初始化命令 → 选择提供 API 凭据
→ 登录 Cordys CRM 个人中心 API Keys 页面取 Access Key / Secret Key
→ 输入连接信息 → 自动加载用户信息 → 自动匹配角色 → 加载角色上下文
```
- **关键点**：① 初始化是**一次性配置**（三参数：域名 + Access Key + Secret Key），之后每次问答免登录；② 凭据在 **CRM 个人中心 API Keys 页面**自助生成（不是管理员手工发）；③ **连接后自动加载用户信息 → 匹配角色 → 加载角色上下文**——角色识别链路（凭据→用户→角色→上下文）是 AI 原生的，用户零配置。
- **转化**：我们平台的接入流程应同样为「**一次性三参数初始化 → 凭据自动解析用户 → 角色引擎匹配 → 注入角色上下文**」，且凭据自助生成（个人中心 API Keys 页）——这是 §6.4 的**端到端实证**，可作为阶段 2 接入流程的验收用例。

**3. 五角色定位表（本篇为「核心关注 / 数据范围 / 主动预警 / 输出风格」四要素，与 §6.2 完全一致）**
| 角色 | 核心关注 | 数据范围 | 主动预警 | 输出风格 |
|---|---|---|---|---|
| 销售 | 我接下来该做什么？ | 我的客户/线索/商机 | 超期未跟进、商机卡顿 | 优先级行动清单 |
| 经理 | 谁需要我关注？ | 全部门+子团队 | 跟进率低、转化骤降 | 团队看板→下钻到个人 |
| 高管 | 公司销售目标达成情况如何？ | 全公司 | 目标缺口、部门偏离 | **趋势分析→对比→预测** |
| 商务 | 合同签对了没有？ | 合同+审批流 | 到期未续、审批卡顿 | 合同状态+到期预警 |
| 财务 | 钱到哪里了？ | 合同→回款→发票 | 逾期、未开票、链路断裂 | 应收全景→催收优先级排序 |
- **增量**：高管输出风格明确为三段链「**趋势分析 → 对比 → 预测**」——这是 crm-funnel 分析类 SKILL 的输出管线（先趋势→再同比/环比→再预测），可作为 stage 2/3 漏斗分析 Action 的输出规范参照。

**4. 六模块 × 自然语言叫法 × 典型查询示例（= 意图→Action 的训练样本库）**
| 模块 | NL 常见叫法 | 核心能力 | 典型查询示例 |

| lead | 线索 | 线索查询、跟进状态 | “查询我名下本周新增的线索”“最近我部门30天没有跟进的线索有哪些” |

**5. contract 二级资源精确清单（= crm-contract / crm-payment Action 表面的对象粒度实证）**
- contract 模块内嵌二级资源：**contract/payment-plan（回款计划）/ contract/payment-record（回款记录）/ contract/business-title（工商抬头）/ invoice（发票）/ opportunity/quotation（报价单）**
- **关键验证**：① **报价单是 opportunity 的二级资源**（`opportunity/quotation`），印证 §6.3 注「官方把报价挂在商机下」→ 我们扩展为独立 `crm-quote` 是正确的差异化；② **工商抬头精确术语 = business-title**（不是模糊的“抬头”），回款域 Action 表面应含 contract/payment-plan + payment-record + business-title + invoice 四对象；③ 这些二级资源与 §5bis 借鉴点 8（ContractPaymentPlan 财务闭环）**完全对齐**——官方实证再次确认回款/发票/抬头是合同模块的子资源，我们阶段 3 的 crm-contract 应含「审批流 + 到期提醒 + 二级资源（回款计划/回款记录/工商抬头/发票）」、crm-payment 应含「回款记录/发票/逾期预警/催收优先级」。
- **转化**：SKILL 内部可以有**层级**——「模块（对象）+ 二级资源（子对象）」两级结构（如 contract/payment-plan），我们平台 Action 表面（`ai-native-action-design`）应支持**命名空间分层**（`crm-contract-payment-plan` 式），而非扁平 Action 列表。

**6. 五个使用示例（新增「区域当月运营复盘」「月度财报」两个场景）**
1. 查询个人名下的线索/客户/商机（销售）
2. 查询团队所有的线索/客户/商机（经理）
3. **查看区域当月运营复盘报告**（区域维度 = 组织层级中间层，是「组织 RBAC（§4.4 organization_id）」在查询场景的直接体现）
4. 查看今日回款情况（财务）
5. **查看月度财报数据**（高管/财务）
- **转化**：③ 明确出现「**区域**」维度——组织 RBAC 不仅是「我的/全部门/全公司」三档，还有**中间层（区域/子团队）**，`organization_id 层级树`（parent_id）应成为上下文分层的标准维度（§4.4 + §6.2 的补充）；④⑤ 说明 NL 查询可直达**运营复盘 / 财报**类聚合分析（crm-funnel/分析 Action 的范围）。

**一句话**：这篇操作教程提供了最细粒度的工程细节——**技能多市场发布（ClawHub/WorkBuddy/GitHub）**实证 §6.4 技能目录的发布形态；**一次性三参数初始化 → 自动加载用户/角色/上下文**实证免登录直连全流程；**六模块 NL 叫法 + 典型示例**成为意图→Action 的训练样本库；**contract 二级资源清单**（payment-plan/payment-record/business-title/invoice + opportunity/quotation）确定 crm-contract/crm-payment 的 Action 表面粒度（命名空间分层）；**区域维度场景**补充组织层级树的检索维度。

### 6.3quinquies 第四篇官方实证：Skills 正式发布公告（「只读数据接口」定位 + 三大功能矩阵 + 四大场景 + 三大量化优势）（2026-08-24 晚）

> 来源：Cordys CRM 官方发布公告《Cordys CRM Skills技能正式发布》（2026-04-07）。**与前几篇的关键差异**：前几篇是「怎么用/怎么配」（交互侧），本篇是「**官方定位文**」——首次明确 Skills 的本质是 **「高质量、强语义的只读数据接口」**，并给出**三大功能矩阵 / 四大场景 / 三大量化优势**。这是对 §6.4「对外技能访问」的**能力边界实证**（外部智能体消费的是「只读查询接口」而非全部写能力），并首次为 SKILL 的**验收指标提供官方量化口径**。

**1. 官方定位：Skills = 「只读数据接口」（对我们最重要的一个定性）**
- 「Cordys CRM Skills 严格遵循官方规范设计，专注于为**大模型提供高质量、强语义的只读数据接口**」。
- **关键发现**：官方对 Skills 的定位是**只读数据接口**（线索/客户/商机/合同/回款的查询与关联），**不是**「读写全能力」——这与 §5bis C 的「两阶段安全写入/绝对禁止删除」安全红线**完全一致**（Skills 对外默认查询，写入走 write-engine + 规则闸）。
- **转化**：我们平台的「对外技能（Skills-as-a-Service，§6.4）」**默认能力 = 只读查询接口**（强语义 + 跨模块关联），写能力是**显式、受限、过规则闸/HITL** 的扩展——这与「下载即用、免登录直连」不冲突，反而更安全。**「只读默认 + 写入显式受限」应成为我们对外技能协议的第一条原则。**
- **【用户补充实证 2026-08-24 晚】Skills 完整定义 = 「基于角色的智能技能集」，API 实际支持读写双能力（口径调和，不矛盾）**：用户确认「Cordys CRM Skills 是基于角色的智能技能集，它让用户可以通过自然语言与 CRM 系统进行交互。Skills 技能依赖 API 接口实现数据的**读取和写入**操作，包括**创建客户记录、录入跟进情况、检索客户信息、统计销售数据**等」。
  - **口径调和**：官方发布公告的「只读数据接口」= **对外默认查询定位**（公告侧重高质量强语义检索，是 Skills 对 LLM 的**默认暴露面**）；用户定义的「读写双能力」= **API 底层能力全集**（接口本身支持创建/录入/检索/统计）。两者互补不冲突：**对外默认只读，写入能力存在但必须显式受限过闸**——与「只读默认 + 写入显式受限」原则精确一致，官方定位描述的是**默认行为**，用户定义描述的是**能力全集**。
  - **四个用例 → Action 表面映射实证（读默认直连、写显式过闸）**：创建客户记录 → `crm-account-create`（**写**，过 write-engine + 规则层 + action-confirm + HITL）；录入跟进情况 → `crm-lead`/`crm-account` 跟进 Action（**写**，同闸）；检索客户信息 → `crm-account` 查询（**读**，默认直连）；统计销售数据 → `crm-funnel`（**读/聚合**，默认直连）。
  - **结论升级**：**SKILL 表面 = 读写混合能力集**（不是纯只读接口），但**读默认直连、写显式过闸**——写操作统一走 write-engine + 表单校验 + 规则层 + 两阶段安全写入（§5bis C），**删除绝对禁止**（安全红线）。这正式确立我们 §6.4 对外技能协议的完整口径：**「读默认直连、写显式过闸」**（官方「只读定位」= 默认性描述，非能力上限）。

**2. 三大功能矩阵（= 我们 crm-lead / crm-opportunity / crm-contract+payment 的官方实证）**
- **多维度线索与客户检索**：按名称/状态/行业/来源/创建时间**复合过滤**；返回线索基础信息 + **深度关联联系人（职能/电话/邮件）**，为 AI 助理提供**完整客户画像**。
- **商机漏斗全量透视**：按预计金额/截止日期/当前阶段**筛选**；快速分析销售全流程，识别处于「方案建议/商务谈判」阶段的核心项目。
- **合同与财务状态实时追踪**：集成合同 + 回款计划的查询技能，按签约主体/回款状态（已支付/待支付）分类。
- **转化**：这三个矩阵 = 我们的 crm-lead（复合过滤 + 联系人关联画像）/ crm-opportunity（漏斗筛选）/ crm-contract+crm-payment（合同财务状态）——官方实证确认**每个 SKILL 的检索维度**（线索：名称/状态/行业/来源/时间；商机：金额/截止/阶段；合同：签约主体/回款状态）应**原生内建为查询 Action 的参数 Schema**（`ai-native-action-design` 参数设计实证）。

**3. 四大场景（= 意图→Action 的验收用例 + 角色矩阵交叉验证）**
1. **查询线索**（筛选查询）2. **查询商机并生成统计摘要** 3. **生成客户画像**（跨模块关联）4. **查看销售团队业绩排行**
- **转化**：①「**查询商机并生成统计摘要**」= NL 直出**聚合分析**（对应 crm-funnel）；②「**生成客户画像**」= **跨模块关联聚合**（对应 linkage-engine 的 Customer 360，§6.3bis + §6.3ter 七大场景）；③「**销售团队业绩排行**」= **经理角色**的团队看板（§6.2 五角色矩阵）。这四大场景可作为**阶段 2 意图→Action 解析的验收场景集**。

**4. 三大量化优势（= 官方首次给出 Skills 的量化价值口径）**
- **全量线索智能检索与汇总**：过去「设置 5-6 个筛选条件」的统计任务 → 「**一句指令**」自动按权重筛选高价值线索，跟进无遗漏。
- **商机进展深度洞察与穿透**：AI 自动**跨模块调取客户与商机详情**，将最后跟进时间与阶段现状一并汇总，快速业务复盘。
- **财务协同与实时回款分析**：无需跨部门索要报表，直接穿透**合同与回款计划接口**，自动按时间排序并匹配对应销售，实时掌控账款进度。
- **转化**：①「5-6 筛选条件 → 一句指令」是 NL→Action 的**成本对比量化口径**（可并入阶段 2/3 验收指标，与 §6.3ter 的「3-5 分钟→3-10 秒」互补）；②「**跨模块调取 + 最后跟进时间 + 阶段现状**」= 客户商机穿透视图的**组成要素**（linkage-engine 输出规范）；③「**穿透合同与回款计划 + 自动按时间排序 + 匹配销售**」= crm-payment 的**回款分析视图规范**（按时间排序 + 按销售归属聚合）。

**一句话**：这第四篇官方实证给出 Skills 的**能力定位与验收口径**——①「**只读数据接口**」官方定位 + 用户补充「**API 读写双能力**」定义 → 我们对外技能协议的完整口径「**读默认直连、写显式过闸**」（官方定位=默认行为描述，用户定义=能力全集，互补不矛盾）；②三大功能矩阵 → crm-lead/opportunity/contract+payment **查询 Action 的参数 Schema 实证**（复合过滤维度原生内建）；③四大场景 → 阶段 2 意图→Action **验收场景集**（含跨模块聚合的客户画像/团队业绩排行）；④三大量化优势 → NL vs 手动操作的**量化成本对比**并入验收指标（与 3-5 分钟→3-10 秒互补）。

### 6.4（重点需求）：「对外技能访问（Skills-as-a-Service）」架构

**这是一个硬性产品需求：未来我们的系统必须支持，通过任意的办公智能体（如 WorkBuddy、千问等）访问或下载 SKILL 后直接进行访问，而无需登录平台（免登录/授权直连），同时做好权限控制与角色对应。**

这意味着我们平台不仅是「对话式 CRM 应用」，还是一个**对外发布技能（Skills）的源平台**——任何办公智能体都能接入消费。架构要点：

1. **技能目录（Skill Catalog）发布**：平台将 §6.3 的 SKILL 清单以**标准化技能包**对外发布（含 skill 元数据/Schema/示例），供 WorkBuddy、千问等外部智能体**发现、下载/安装、调用**，如同 Cordys CRM Skills 通过 GitHub 仓库发布、在千问中一键安装。
2. **免登录接入（授权直连）**：外部智能体不要求用户在 CRM 平台登录，而是通过**受控接入凭证**直连能力层（对标 Cordys 的 CORDYS_ACCESS_KEY / SECRET_KEY 思路，但改为**平台级更安全的 OAuth2/JWT/短期令牌**）。
3. **权限控制**：**每个 Skill / 每个 Action 绑定最小权限**（RBAC）。外部智能体只能执行其授权范围内的操作；写操作仍需 HITL 审批闸（§4.2 借鉴）、关键 Action 需确认（action-confirm，继承 PDM/P2P 已验证范式）。**权限检查统一在平台侧执行**，外部智能体不绕过。
4. **角色对应（自动识别）**：接入时**自动识别调用者身份与角色**（对标 Cordys「基于 API 凭据自动匹配角色」），进而自动套用该角色的**数据范围 / 关注重点 / 主动预警 / 输出风格**（§6.2 角色四要素）——即把 `ai-context-layering` 治理决策层**贯彻到外部智能体进来的每一次调用**。
5. **统一的技能协议**：对外暴露**统一的技能调用协议/接口**（Action 表面 + 意图 NL 描述 + 角色上下文），让 WorkBuddy、千问等**跨智能体一致消费**，而不是为每个智能体各做一套适配。
6. **审计与闭环**：外部智能体的调用**全量进事件总线与审计日志**（供 `ai-event-driven-evolution` / `ai-capability-audit` 闭环，验证能力确实被生产使用）。

**一句话**：我们平台要交付的不是「登录后用」，而是「**下载即用、免登录直连、权限与角色在平台侧统一管控**」的对外技能源——这是企业AI销售决策平台区别于传统 CRM 的**关键产品形态**。
