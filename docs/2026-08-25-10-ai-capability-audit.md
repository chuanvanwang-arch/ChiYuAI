## 0. 核心立场：审计事件流原生内建，而非外挂日志

> **审计不是「旁路日志表」，而是贯穿所有写操作与对外技能调用的审计事件流（Audit Event Stream）——它从第一行代码长出来，与粒子写事件同生命周期，是 D12「原生化」总差异在治理维度的直接体现。**

对 CRM 销售域的关键判别（呼应 §5ter-quater Q.19 D12 + 总体架构三不变量）：

- **官方审计 = 外挂日志**：CordysCRM 的审批记录/价格变更日志是叠加在 Java/MySQL 之上的独立日志表（§5ter.618「官方=审批日志表」、§5ter.544「官方=表+日志」），与业务写操作分离，事后写入、可绕开、无强制。
- **我们审计 = 审计事件流原生内建**：每一次写操作（人 / 智能体 / 外部技能）走写通道三闸（规则层 → action-confirm → HITL）后，**强制落一条审计事件**进事件总线，与粒子写事件同源广播；外部技能调用全量进事件总线与审计（§6.4 第 6 条）。**没有「无声写入」，没有「绕过闸门的写」，没有「审计可关可绕」**。
- **机制级强制**：审计落点不在 Action 业务逻辑里「记得调一下」，而在写通道的**统一写钩子**里——任何写操作只要进粒子写通道，就进审计；写钩子缺失 = 架构不变量违约（P0 缺口）。这与「禁删从 Action 表面移除 + 输出管道脱敏」（D6 红线机制化）同构：审计不是提示词约束，是机制不可能缺。

## 1. 方法论依据（提炼 SKILL 核心法则 / 铁律 / 判据）

本能力的方法论源 `ai-capability-audit` 是一套**跨域通用**的审计方法论。核心法则提炼如下，实例化到 CRM 时保持中性，不引入任何别项目专有名词（如 IPD/PDM/P2P/Agent2b 等）。

### 1.1 四条铁律

| # | 铁律 | CRM 实例化含义 |
|---|---|---|
| 法则 1 | **审计以代码为准，不以文档为准**（「检查代码不是文档」） | 能力「已落地」的断言必须有代码证据（文件:行号）。文档写了审计、注释声称审计、测试通过≠审计已落地。 |
| 法则 2 | **缺口判定必须 grep 证据** | 任何「某能力未审计 / 某域未进审计」的判定，须 `grep` 写钩子 / 事件发射点 / 审计表落点验证；禁止仅凭文档或直觉声称。 |
| 法则 3 | **10 大能力矩阵无空白** | 审计能力自身也要被审计对象覆盖：粒子/本体/上下文/记忆/Action/编排/事件/门户/反馈/审计——每个能力在 CRM 域的「业务设计输入」必须可映射、可验收（Q.20 矩阵无空白）。 |
| 法则 4 | **缺口回补两类分流** | 缺口分「补充完善（项目代码修复）」与「更新 SKILL（方法论缺口回写）」两类，分别给落点，禁止混为一谈。 |

### 1.2 核心判据（动态引用、不内嵌）

- **判据动态引用**：10 大能力各自的落地判据来自对应 ai-* SKILL（核心承诺/自检清单），审计时按能力读取，确保判据随 SKILL 演进同步（不把判据写死在本文档）。
- **三查法**：`grep -n <关键标识>` 定位 → `Read` 上下文确认 → 交叉引用调用点。落地判定 = 函数存在 **且** 有调用点（如「审计写钩子」必须被粒子写通道实际调用，否则仍是未落地）。
- **缺口三要素**：① 断言（如「外部技能调用未进审计」）→ ② 代码证据（如 `grep external_call` 0 命中审计表）→ ③ 影响（如「外部写操作不可追溯」）。
- **0 数据 ≠ 闭环**：审计事件表结构在、写钩子在，但若业务表/事件表 0 条 = 审计闭环断点。判据须直查数据源（审计事件集合是否有真实行），而非只读代码。
- **演示值审计**：看板/审计报表字段若硬编码（如 0/0、'stable'、tokensConsumed=0）→ 逐一 grep 聚合源；硬编码项 = 「前端就绪、后端假数据」缺口。
- **疑似缺口必须下钻**：先验证缺口是否真实存在——存在则确认，不存在则修正表述（不把「未读全代码」误判为「未落地」）。

### 1.3 对话式工作流边界（本设计为「设计态」，非「运行态审计」）

> SKILL 本身是「对话式工作流」：先互动确认范围/判据 → 代码级验证 → 对话确认缺口分级 → 建议方案 → 产出报告。本文档是**设计态**的能力落地设计（把方法论固化为 CRM 审计事件流的架构与验收基线），不是一次具体的代码审计执行。运行态审计的执行流程沿用 SKILL 七环节，本文档第 3.3 节给出其在 CRM 的代码级落地形态。

## 3. 落地设计

### 3.1 审计事件流数据结构（AuditEvent，与粒子写事件同生命周期）

审计事件流是事件平面（L2）的一等公民，持久化于事件总线。一次写操作产生**一条粒子写事件 + 一条审计事件**（同源广播，互不阻塞主事务）。

```
AuditEvent {
  event_id          UUID              // 事件唯一 ID（幂等去重键）
  event_domain      枚举              // 5 事件域：task/trace/approval/particle/payment
  op_type           枚举              // create/update/delete(禁止但实际留痕)/approve/reject/external_call
  actor_id          PERSON_ID         // 操作人（人/智能体 worker/外部调用者映射的绑定角色）
  actor_role        角色标签          // 来自 RBAC 注入（L4 治理决策层）
  org_id            ORG_ID            // 组织 RBAC 贯穿，数据范围过滤
  action_namespace  字符串            // 如 crm-contract-payment-plan（命名空间分层）
  action_name       字符串            // 如 crm-contract-create
  target_particle   粒子类型          // CRM_DEAL / CRM_PRICE_LIST / APPROVAL_INSTANCE ...
  target_id         实体 ID           // 双轨别名↔物理 ID
  before_state      JSONB             // 写前快照（关键字段增量，非全量）
  after_state       JSONB             // 写后快照
  rule_gate         判定结果          // 规则层：状态机合法性 / 金额超 20% 等
  confirm_by        PERSON_ID         // action-confirm 确认人
  approval_instance_id  实例 ID       // HITL 审批流实例（四大写域）
  source            枚举              // human / agent / external_skill
  // —— 外部技能调用专用字段（B3） ——
  skill_id          技能包 ID         // §6.4 技能目录发布的标准化包
  caller_agent      外部智能体标识    // WorkBuddy / 千问 ...
  credential_id     接入凭证 ID       // 免登录直连短期令牌（请求结束即注销）
  rbac_decision     JSONB             // 平台侧统一权限判定（最小权限闭包结果）
  reason            why 载体          // 写操作理由（如 price_change_reason / stage_change_reason）
  chain_hash        防篡改链          // 前序事件 hash + 本事件 hash（篡改可侦测）
  created_at        timestamp
}
```

**设计要点**：
- **写前/写后双快照 + reason**：满足记忆系统 why 硬门槛（价格变更必填 `price_change_reason`、阶段转换必填 `stage_change_reason`），审计事件同时是决策理由载体。
- **chain_hash 防篡改链**：审计事件按时间序哈希成链，事后篡改任一记录即断链——治理级不可抵赖（对应 D12 机制级强制）。
- **source + skill_id 双标识**：外部调用与人/智能体调用在同一张表、同一套钩子，区别只在 `source=external_skill` 及其专属字段——避免「两套审计」分裂。

### 3.2 写钩子：所有写操作 / 对外技能调用落审计（机制级强制）

审计落点 = **粒子写通道的统一写钩子（audit hook）**，位于总体架构 §4 写通道「粒子写通道（事务写入 + 触发粒子写事件）」之后、与粒子写事件并行广播。

```
写通道（人/智能体/外部技能）
  → 规则层（能不能写）
  → action-confirm（这次写要不要确认）
  → HITL 审批流（四大写域）
  → 粒子写通道（事务写入 + 触发粒子写事件）
  → 【auditHook】构造 AuditEvent（actor/role/org/action/target/before-after/reason/...）
       ├─ source=external_skill 时补齐 skill_id/caller_agent/credential_id/rbac_decision  ← B3
       └─ 广播至事件总线（与粒子写事件同源）→ 持久化审计事件集合
```

**强制不变量（架构违约即 P0 缺口）**：
1. 钩子是写通道的**必经节点**，不在各 Action 业务代码里「各自记得调」。任何写操作只要进粒子写通道，就进审计。
2. 外部技能调用**不绕过**写钩子：§6.4 免登录直连入口在平台侧统一执行权限判定后，写操作仍走同一写通道 → 同一钩子（§6.4 第 3 条「权限检查统一在平台侧执行，外部智能体不绕过」）。
3. **读操作不写审计**（与「读默认直连」一致）；审计只覆盖写操作与外部调用。

### 3.3 代码级审计流程（grep 证据 + 缺口判定，实例化 SKILL 七环节）

运行态审计（对已完成开发做能力落地审计）在 CRM 的代码级落地形态：

| 环节 | CRM 落地动作 | grep / 验证点 |
|---|---|---|
| ① 探索上下文 | 列 `src/`（粒子写通道 / Action 表面 / 外部技能入口 / 事件总线）+ 历史审计基线 `docs/*-audit*.md` | `Glob src/**`；读历史审计避免重复 |
| ② 判据提取 | 按 10 能力顺序从对应 ai-* SKILL 提取核心承诺 | 动态读 `~/.workbuddy/skills/ai-<name>/SKILL.md` |
| ③ 代码级验证（强制） | 对每能力「已落地/缺口」grep 写钩子/事件发射点/审计表落点 | `grep -n auditHook`、`grep -n emitAudit`、`grep -n external_skill` 落点验证 |
| ④ 判定分级 | ✅/⚠️/❌ + P0/P1/P2 | 缺口标优先级；部分=钩子在但 12 域未全覆盖 |
| ⑤ 对话确认 | 呈现缺口分级表确认优先级（一次一问） | 用户确认后进建议方案 |
| ⑥ 建议方案 | 两类分流：①补充完善（代码修复落点）②更新 SKILL（方法论缺口回写） | 每项可执行有落点 |
| ⑦ 产出报告 | 存 `docs/YYYY-MM-DD-<topic>-audit.md` | 自查占位符/矛盾 → 用户审查 |

**CRM 特有验证点（缺口三要素示例）**：
- 断言：「外部技能调用未进审计」→ 证据：`grep -n "source.*external_skill"` 在审计表写入处 0 命中 → 影响：外部写操作不可追溯 → P0。
- 落地判定：「审计表存在」≠「已落地」——须 `grep` 出 `auditHook` 被粒子写通道**实际调用**（调用点存在）才算 ✅。
- 0 数据核查：审计事件集合直查行数；若钩子有但 0 条真实审计事件 = 闭环断点（同 SKILL「0 数据 ≠ 闭环」）。

### 3.4 10 大能力覆盖矩阵（验收基线，基于 Q.20）

本矩阵是「10 大能力矩阵无空白」法则在 CRM 的验收基线：每个能力在 CRM 的业务设计输入 + 审计核验点（应存在的代码/表/端点标识）。

| # | 能力 | 从 Q.20 得到的业务输入（须覆盖） | 审计核验点（grep 标识） |
|---|---|---|---|
| 1 | particle | 12 域粒子化 + 状态机内建 | `grep particle.*lifecycle` / 写钩子覆盖粒子写 |
| 2 | ontology | 写时向量化 + 本体边 + 连接器闸 | `grep ontologySync` / 写时钩子含审计 |
| 3 | context | 角色七要素=L4 + 视图物化 + 区域注入 | `grep contextLayer` / 审计事件带 actor_role+org_id |
| 4 | memory | 跟进流 / 审批快照 / 凭证记忆 | `grep memory.*snapshot` / 审计事件可进记忆 |
| 5 | action | crm-* Action 表面 + 命名空间分层 + 写时计算 | `grep action-confirm` / 每个写 Action 过钩子 |
| 6 | orchestration | HITL 闸 + kanban 派发 + 待办聚合 | `grep kanban.*dispatch` / 任务状态转换留审计 |
| 7 | event | 预警事件源 + 补偿机制 | `grep emitEvent` / 事件进总线即进审计 |

| 10 | **audit** | **价格变更/审批=事件流；12 域进审计；外部调用全量审计** | **`grep auditHook` + `grep external_skill` 全量落点** |

> 矩阵无空白 = 10 能力每行都有业务输入 + 可 grep 的核验点。任一能力无输入或无可验证代码点 = 矩阵缺口（回 Q.20 补映射或回 SKILL 补判据）。

### 3.5 外部技能调用全量审计（§6.4 事件总线 + 审计，B3）

§6.4 第 6 条「外部智能体的调用全量进事件总线与审计日志」的落地链路：

```
外部办公智能体（WorkBuddy/千问）
  → 一次性三参数初始化（DOMAIN/ACCESS_KEY/SECRET_KEY）→ 平台侧解析用户→匹配角色→注入上下文
  → 免登录直连调用本平台 SKILL/Action（读默认直连 / 写显式过闸）
  → 平台侧统一权限判定（RBAC 最小权限闭包，外部不绕过）
  → 写操作仍走写通道三闸 → 粒子写通道 → auditHook
       └─ source=external_skill：补齐 skill_id / caller_agent / credential_id / rbac_decision
  → 审计事件进事件总线 → 持久化 → 供 ai-event-driven-evolution / ai-capability-audit 闭环
```

**核验点**：① `grep` 外部技能入口有审计钩子挂接；② `grep` 审计表 `source=external_skill` 字段写入；③ 直查审计事件集合，外部调用有真实行（0 数据 = 闭环断点）。

## 4. 与其他能力 / 四平面的接口

审计能力挂 **L2 事件平面**（总体架构 §1 四平面矩阵），是横切接线层，**贯穿全部平面**：

| 接口方 | 接口性质 | 说明 |
|---|---|---|
| **事件平面（L2，自身平面）** | 消费全部事件 | 审计事件流与粒子写事件同源广播；审计是事件总线的原生消费者之一（与本体构建/记忆/预警/反馈并列，总体架构 §1 事件平面职责）。 |
| **粒子平面（L1）** | 校验写操作 | 审计写钩子挂在粒子写通道末端，校验每次写（人/智能体/外部）都落审计；粒子状态机转换的 `before/after` 是审计快照来源。 |
| **智能体平面（L3）** | 校验 Action 表面 | 所有写 Action（crm-*）过写通道三闸即过审计钩子；外部技能调用（§6.4）统一在平台侧进钩子，外部不绕过。 |
| **呈现平面（L4）** | 回显审计轨迹 | 门户工作台可展示「谁在什么角色下写了什么」；审计报表来自审计事件集合（非硬编码）。 |
| **ai-event-driven-evolution（事件）** | 双向 | 审计事件进事件总线被进化闭环消费（技能沉淀/补偿）；审计本身是预警与进化的数据源之一。 |
| **ai-feedback-loop（反馈）** | 溯源 | 反馈回路的「计划 vs 实际 / 预期 vs 实际」对账数据，须可溯源到对应审计事件（谁改的、何时改的）。 |
| **ai-memory-lifecycle（记忆）** | 快照复用 | 审批记录审计事件 = 记忆快照（跨会话可引用）；审计事件的 why 载体（price_change_reason 等）同时是记忆系统的决策理由。 |
| **其他 9 能力（ai-*）** | 反哺 | 运行态审计（§3.3）的结论反哺其他 9 能力的 SKILL 与实现——缺口回补两类分流（补充完善 / 更新 SKILL），是审计能力的天然出口。 |

**贯穿不变量（总体架构 §5）**：写操作必有事件、必有审计、必有轨迹——审计是这条不变量的强制执行者；读操作直连、写操作过闸——审计钩子保证「没有绕过闸门的写」。

## 6. 不做的事（YAGNI + 不借鉴）

- ❌ **不借鉴 CordysCRM 外挂日志式审计**：官方审批日志表 / 价格变更日志表是叠加在旧底座上的独立日志，与写操作分离、可绕开——我们拒绝此形态，审计事件流原生内建为写通道必经钩子（D12 原生化总差异的治理体现）。
- ❌ **不做「旁路可选审计」**：审计不是可开关的配置项、不是业务代码里「记得调一下」的软约束——机制上不可能缺（与禁删从 Action 表面移除同构）。
- ❌ **不做第二套外部调用审计**：外部技能调用与人/智能体调用共用同一写钩子、同一张审计表（区别仅在 `source` 字段），不另建「外部审计子系统」。
- ❌ **不审计读操作**：读默认直连、不写审计（与总体架构读写双通道一致）；审计只覆盖写操作与外部调用。
- ❌ **不把审计判据内嵌写死**：10 能力判据动态引用对应 ai-* SKILL，本能力不维护一份静态判据表（避免与 SKILL 演进脱节）。
- ❌ **不在本设计态执行具体代码审计**：本文档是能力落地设计（架构 + 验收基线），运行态审计按 SKILL 对话式七环节执行（§1.3 边界）。
